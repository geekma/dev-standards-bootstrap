# 状态/触发链路审计（State-Trigger Audit Methodology）

> **定位**：本文件承载"状态/触发链路类变更"的审计方法——凡"某处状态变化会连锁触发行为"的链路均属此类：前端响应式框架、后端事件驱动服务、消息队列、工作流引擎、ORM/缓存钩子。规范落点：§2.5 阶段 2（技术影响·隐式链路三向遍历）与 §2.5 阶段 6（同族推演）；选级归属见 `docs/METHODOLOGY.md` §3.2 / §3.6。
> **读取时机**：阶段 2 做影响分析且变更命中状态/触发/事件链路时；阶段 6 修复缺陷写根因表前；阶段 8 Review Agent 审查缺陷修复完整性前。

---

## 1. 六条通用教训（为什么必须成体系审计，而不是逐个打补丁）

1. **规格先行，审计在后**——先写下不变量（"什么情况下允许发生 X"），再开始找违反项。没有成文规格，"遗漏"无法定义：你只能查"有没有 bug"，查不了"有没有第三种触发方式"。规格只在需求沟通里没落盘时，审计必然多轮返工。落点：不变量入 `01-spec.md`（REQ 验收标准）。
2. **正向调用图对隐式边召回率为 0**——`grep 调用点` 只能找到显式调用。状态链路缺陷高发区在隐式边，这些地方代码里**没有任何关键字可 grep**：
   - 框架响应式：watcher / computed / 数据绑定（改一个字段，三层之外触发行为）；
   - 事件机制：事件总线、发布订阅、observer、回调注册；
   - 中间层转发：HTTP 响应处理器、消息队列消费者、路由/生命周期钩子；
   - ORM/缓存钩子：save/update 监听器、脏检查。
3. **修一个根因，必须做同族推演**——每个 bug 问一句："还有哪些路径共享这个根因模式？"（实例：同一根因最终找到 4 条旁路）。不做这步，同一族缺陷会以不同表现反复出现——历史上"改了无数遍"的顽固问题，几乎都是同族缺陷被当独立 bug 逐个打。
4. **测试全绿 ≠ 覆盖完整**——测试面 = 开发时已知的面。未审计路径连用例都不存在，绿是幸存者偏差。全量回归证明的是"没改坏已知的东西"，不证明"没漏未知的东西"。
5. **观测有盲区，日志不能当完整性证据**——监控/日志只覆盖已埋点的路径。用运行日志还原根因很有效，用它推断"系统只有这些路径"是幸存者偏差——看不见的地方一行日志都不会留。
6. **反应式修复的成本是指数的**——每轮只修最新报障 → 同族缺陷以新表现回归 → 再修 → 再回归。用户每问一次"还有没有遗漏"，本质是在逼你补一轮该做的系统性迭代。n 个独立旁路 ≈ n 轮返工；一次性枚举 ≈ 1 轮。

## 2. 六步审计清单（阶段 2/6 按序执行）

```
□ 1. 规格先行：从需求提炼不变量，落成文档（"允许什么、禁止什么、频率上限"→ 01-spec）
□ 2. 枚举事件源（典型 6 类）：用户输入 / 系统自动事件 / 连接与会话生命周期 /
     导航与页面生命周期 / 定时器与调度 / 响应与回调处理器
□ 3. 三向遍历，各出一张清单（落 02「隐式链路三向遍历」节）：
     正向——谁显式调用目标行为（grep 调用点）
     反向——哪些状态变更会经 watcher/emit/回调/钩子间接到达目标行为
     矩阵——每个事件源的处理归宿，逐个标注"归入哪条不变量"
□ 4. 用不变量逐条核对归宿清单 → 产出违反项清单 → 才开始改码（先分析后方案，§2.5 阶段 2 强制顺序）
□ 5. 每修一个根因，强制同族推演："还有哪条路径共享这个根因模式？"
     结论写入 BUG 根因表「同族推演」行（§4 CHG 模板）
□ 6. 收尾三件套：残余项登记 FU-xxx（06-delivery）/ 更新规则文档（含精确代码位置）/
     为每个修复写防回归锚点（TC 入 04，证据入 05 批次）
```

## 3. 收敛信号（何时可以停止审计）

- 连续 2 轮全维度遍历无新发现 → 收敛，停止；
- 每个事件源都有明确归宿、且全部归入不变量 → 完整；
- 剩余项全部是"需要产品/架构决策"而非"事实未查明" → 可以收工（决策类剩余项登记 FU-xxx 并标注决策方）。

**一句话版本**：先把"什么算遗漏"写成文，再把事件的每一条来路（含看不见的来路）枚举成表，逐条对照——**review 的完整性由方法保证，不由轮数保证**。

## 4. 三个反模式（Review Agent 出现即退回）

| 反模式 | 信号 | 处置 |
|---|---|---|
| 修完即收工 | CHG 只验证了本次修复，根因表无「同族推演」行或同族行只写"无"却无扫描过程 | 阶段 6 B 层退回 |
| 用修复历史当覆盖证据 | 以"之前修过类似的"论证"这族已扫完" | 无效论证，要求按本清单重新枚举 |
| 规格口口相传 | 不变量只存在于需求沟通或某次 commit 注释，01-spec 无成文记录 | 要求落盘后重审 |

## 5. 与既有产物/方法论的边界（防重复枚举、防互相替代）

- **与阶段 4「SC-xxx 五维业务场景枚举」的关系**：五维是**业务语义视角**（要测哪些场景），本方法六类事件源是**技术事件视角**（行为从哪里来），二者不可互替。命中状态/触发链路的变更两者都要做；04 的 SC 清单可引用 02 的事件源矩阵作为枚举输入。
- **与 02「爆炸半径」的关系**：爆炸半径回答"我改了会波及谁"（静态拓扑视角），隐式边反向遍历回答"谁会隐式触发我"（动态链路视角），二者互补，缺一不可。
- **与阶段 6「根因推导（排除假设法）」的关系**：排除假设是**纵向备择排除**（这个分歧点是不是别的原因导致），同族推演是**横向模式扫描**（这个根因模式还出现在哪些路径），修复类 CHG 两者都必须留痕，不可用一个顶替另一个。
- **与全量回归/覆盖率的关系**：回归与覆盖率证明"已知面没改坏"（教训 4），本方法补的是"未知面的枚举"——全绿不是跳过本方法的理由。
