# 代码规范（Development Methodology）

> **定位**：本文件是编码阶段（规范 §2.5 阶段 5）与 Review 阶段（阶段 8）的工程决策依据——每条规范都同时回答"为什么用"与"为什么不用/何时降级"。选级归属见 `docs/METHODOLOGY.md` §3.5（本文件承载 KISS/YAGNI 的 M0 细则与 SOLID/DRY 的 M1 细则，及七大工程维度）。
> **读取时机**：写任何业务代码前；Review Agent 审查编码质量前；阶段 3 做技术选型引用本文件时。

---

## 1. 原则冲突裁决顺序（唯一权威）

四条基础原则冲突时，按以下顺序裁决（高优先者胜）：

**KISS > YAGNI > DRY > SOLID**

- KISS 赢 DRY：**重复优于错误的抽象**。两段"看起来像"的代码若演化方向不同，强行合并比保留重复更贵。
- YAGNI 赢 SOLID：不为臆想的扩展点设计接口分层。扩展点须有已发生的证据（≥3 变化点，见 §5）。
- 任何原则赢不过"需求本身"：规范与门禁（§0、门禁 1–5）永远优先于本文件。

## 2. 基础原则（为什么用 + 为什么不用）

### 2.1 KISS（M0）

- **为什么用**：简单方案的验证成本、回归成本、Review 成本都最低；AI Agent 重构复杂代码的出错率随复杂度非线性上升。
- **为什么不用/误用警告**：KISS 不等于"能跑就行"——判空、异常兜底、资源释放是正确性的一部分，砍掉它们不是 KISS 是缺陷。
- **操作判据**：新增代码若无法用一句话说清"它负责什么"，即超出了 KISS 边界，须拆分或简化。

### 2.2 YAGNI（M0）

- **为什么用**：未被需求引用的代码（REQ 追踪不到的，门禁 4 视为游离代码）没有对应测试动机，是回归盲区。
- **为什么不用/降级场景**：以下三类**不算**臆想需求，YAGNI 不适用——① 安全冗余（如输入校验、防重放）；② 规范明确要求的产物（如降级路径，§2.9.3）；③ 01-spec 已登记且排期的需求（有 REQ 编号即非臆想）。
- **操作判据**：写任何"以后可能用到"的参数/分支/表字段前，先回答它对应哪个 REQ；答不出即删。

### 2.3 DRY（M1）

- **为什么用**：同一业务规则存在两份实现时，修改必漏其一——这是缺陷的头号来源之一。
- **为什么不用**：① 巧合性重复（两段代码只是现在恰好相同，业务演化方向不同）；② 跨模块的"重复"（各模块各自拥有的常量/文案，强行共享引入无谓耦合）；③ 重复不足三次（Rule of Three，第一次重复容忍，第二次警觉，第三次才抽象）。
- **操作判据**：抽象前先问"这两处未来会因同一个原因、在同一个时间被修改吗"——否，则不合并。

### 2.4 SOLID（M1，逐条）

| 原则 | 为什么用 | 为什么不用/降级 |
|---|---|---|
| **S** 单一职责 | 一个模块只有一个变更理由；改动影响面可预测（联动 02 影响分析） | 拆分粒度过细导致"一行类"泛滥；判据是变更理由而非行数 |
| **O** 开闭 | 变化点到来时新增而非修改，降低回归面 | 无变化证据时预留扩展点 = 违反 YAGNI；O 的成本须由真实变化点买单 |
| **L** 里氏替换 | 子类可无感替换，是多态正确性的契约 | 为复用 5% 代码而继承、却违反父类语义——此时应改用组合 |
| **I** 接口隔离 | 消费方只依赖它用到的方法，缩小编译/运行耦合 | 接口数膨胀到超过实现数即过度；小接口须由真实消费方需求驱动 |
| **D** 依赖倒置 | 高层策略不绑定低层细节（如换 LLM 供应商不动业务层） | 简单稳定依赖（工具类、标准库）再包一层接口纯属仪式 |

**降级场景（统一）**：一次性脚本、标注了生命周期与废弃日期的原型、总行数 <50 的模块——SOLID 降级为建议，Review 不作退回依据。

## 3. 七大工程维度

### 3.1 命名

- 名词承载领域语义，必须与 01-spec 术语一致（需求写"会话"，代码不得写 conversation/session 混用）。
- **禁止空名**：`data`、`flag`、`info`、`temp1`、`handle` 只允许出现在序列化契约字段或第三方 SDK 约束中，业务代码一律命名到"看名知义"。
- 布尔命名 `is/has/can` 前缀；函数为动宾结构（`parseSuggestion`，而非 `suggestion2`）。
- **为什么不用（防洁癖）**：不为改名而发独立变更——命名修改必须随行为变更同一 CHG 走（门禁 4 追踪），纯改名单独 PR 属于噪音变更。

### 3.2 复杂度控制

- 单函数圈复杂度阈值 **≤10**（团队可调，但阈值须显式写在 03 并保持仓库内统一）；嵌套深度 **≤3**。
- 超阈值的标准处理：卫语句提前返回 → 拆函数 → 表驱动（M2，见 §5）；**禁止**用注释"解释"复杂分支来替代消解。
- **为什么有阈值**：圈复杂度与缺陷率线性相关是经典实证结论；对 AI Agent 而言，复杂函数是静默漏改分支的高发区（联动阶段 4 逻辑分支覆盖维度）。

### 3.3 耦合与内聚

- 内聚判据：一个模块的所有成员服务于**同一个变更理由**；出现第二个理由即拆。
- 禁止循环依赖；依赖方向固定为"外层 → 领域层"，领域层不得 import 外层类型。
- 跨层数据结构直接引用（Controller 返回 Entity、领域层持有 DTO）属于数据建模违规，按 `data-structures.md` §2 转换规则处理。

### 3.4 错误处理

- **禁止空 catch / 吞异常 / 返回 null 代替错误**——错误必须二选一：处理（含降级）或上报（抛出/记录后终止当前链路）。
- 错误信息三要素：发生了什么 + 原因（含上下文标识）+ 下一步怎么办（可操作）。`e.getMessage()` 直接抛给用户不算合格错误。
- 外部调用（LLM/HTTP/DB）错误须分类：**可重试**（超时、限流）/ **不可重试**（鉴权、参数）/ **需降级**（内容合规拒绝、模型不可用）——联动规范 §2.9.3，分类结果映射到 03 的错误码表，禁止同一错误码混装多类语义。
- **为什么不用（防过度）**：内部私有函数间不必层层 try-catch 包装——在知道如何处理的边界统一处理一次即可；层层包装 + 重新包装异常是另一种噪音。

### 3.5 日志

- 关键路径必打：入口（含关键参数，脱敏后）、外部调用前后、降级触发、最终出口。
- 级别语义：ERROR = 需要人介入；WARN = 自动兜底成功但需关注；INFO = 关键路径里程碑；DEBUG = 细节（生产默认关闭）。
- **禁止**：日志输出 PII（规范 §2.9.4 严重违规）；用 `log.error` 代替错误处理（打了日志继续跑）；同一事件多级重复打印。
- 结构化日志字段（traceId/changeId 等）随事件携带，禁止依赖"上下文日志"隐式拼接。

### 3.6 并发

- 默认不可变共享（联动 `data-structures.md` §4.1）；需要可变共享时，作用域收到最小（单实例内 / 单请求内）。
- 引入锁/线程池必须回答三问：锁粒度是否最小？锁内是否可能再获取其他锁（死锁）？等待是否有超时？
- 并发修改属于九类覆盖维度的"并发"维度（规范 §2.5 阶段 4）——**加了并发代码但没有并发测试 = 阶段 4 覆盖缺口**，测试 Agent 退回。

### 3.7 资源管理

- 获取即释放：`try-with-resources` / `finally` / `defer`，禁止"用完手动 close"的裸管理。
- 一切外部资源（连接、HTTP 客户端、流）必须配置**超时**；无超时的外部调用不允许合入（联动规范 §2.8）。
- 泄漏兜底：长生命周期进程须有资源监控指标（连接池水位等），只增不释放的资源须在 02 风险节登记。

## 4. 与门禁/验收的联动

- **B 层**：Review Agent（阶段 8）按本文件 §2、§3 逐条核对；M0 条目违反（吞异常、无超时外部调用、空名）列入问题分级"严重"；M1 条目违反列入"中"。
- **A 层**：本文件**不新增**机器校验（agent-gate 不检查编码风格——那是 linter 的职责，属于目标仓库工具链而非治理包）；治理包只保证"有没有走阶段产物"，本文件保证"走得对不对"。
- 命名/风格类由目标仓库自身 linter 兜底，不在 07-review-report 重复登记（除非 linter 缺位，此时按 §3.1 手工核对）。

## 5. 反向检查（防无脑套用，Review 必看）

**场景：一个简单 if/else 分支（两种会员等级走不同折扣率）。**

- 错误路径：写成 Strategy 模式 + 两个实现类 + 工厂——变化点只有 2 处且无增长迹象，未命中 M2 触发条件（≥3 变化点），按 `METHODOLOGY.md` §3.3 判过度设计，退回。
- 正确路径：直接 if/else + 每分支单测。当且仅当第三种等级出现时，重构成表驱动（Map<等级, 折扣率>）；第四种及以上且含复杂逻辑时，才评估 Strategy。
- **Review 操作**：见到新增的任何模式/抽象层，先问"证据在哪"（≥3 变化点或 02 影响分析中的明确预警），答不出即按 `METHODOLOGY.md` §4 判否并记入 07 问题分级。
