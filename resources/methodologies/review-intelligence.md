# 评审智能契约（Review Intelligence Contract）

> 文档编号：methodologies/review-intelligence.md（方法论层；随 `bootstrap --core` 下发）
> 定位：规范 §2.2 管"谁必须评审、独立性到哪一级"；本文件管"评审怎么带着项目背景、专业能力与批判性去判断，以及评审执行体/模型怎么选"。
> 唯一权威关系：风险分级与四主体互异仍以 §0.5 / §2.1 规则 10 为唯一权威；本文件不另立等级、不替代门禁。

## 0. 铁律（不可协商）

1. **生产与评审分离**：同一变更内，作者、实现、测试、评审四主体互异；评审不得与生产同会话、同执行主体，更不得自签。编排 Agent 不得兼任任一签署（§2.1 规则 10）。
2. **评审必须带项目背景**：评审前装载项目快览、P12 领域上下文、P01–P04 相关章节、bugfix-log 同族教训、FU 台账与本变更产物；禁止脱离项目实际做模板泛评。
3. **评审必须专业对口**：架构评审看架构先进性与覆盖面；代码评审看安全、漏洞、性能、缺陷与业务合理性；UI 变更另看 UX/UE 与可达性。能力不匹配的评审视为无效。
4. **评审必须批判**：至少给出 1 条有证据的发现或显式达标确认，并给出 1 条可执行改进；零发现零建议 = 泛评，退回（§2.2 增量承诺）。
5. **高成本模型必须用户确认**：AI 只能列出候选、能力与成本档位，不得自行选择高成本模型；用户确认后才可进入评审。未确认即用高成本档 = 门禁违规。

## 1. AI 判断原则（不写死）

- 门禁只校验**结构、证据、独立性、成本确认**；专业结论由评审 AI 基于证据判断，禁止用固定分数/固定关键词替代判断。
- 每个判断必须可追溯到证据：`路径:行号`、REQ/DES/TC 编号、日志片段、项目背景条目或 bugfix-log 教训。
- 评审 AI 可以推翻引擎建议/前序结论，但必须在 `07-review-report.md` 写明「推翻对象 + 证据 + 复核主体」；无证据的推翻无效。
- 自适应判定（测试选节、预算、换挡、是否加严）由 AI 给出判断与依据，引擎建议只作输入；判断记录落 `00-intent.md`「AI 判断记录」或 09「重要上下文」。

## 2. AI 子代理派发输入契约（评审 / 测试 / 勘探 / 实现通用）

派发任何 AI 子代理（评审、测试、勘探、实现、交付）时，prompt 必须按 P0–P8 装配；**一句话 role prompt 不合格**。评审环节为最强约束（缺项目背景直接退回），其余环节同骨架按需裁剪，但 P0/P2/P3/P8 不得省。

| 组 | 必含内容 |
|---|---|
| **P0 任务** | 角色、变更号、阶段、读写边界（只读 / 可写面）、完成判据 |
| **P1 项目** | 系统做什么与用户是谁、架构形态与技术栈、规模与上手路径、行业与合规约束、敏感数据面、UI 面 |
| **P2 变更** | 类型 / 规模 / 风险等级 / `ui_change`、敏感面、功能目的、业务规则、挂靠 UJ、预期结果、非目标 |
| **P3 输入** | 受影响 REQ-DES-TC、产物路径（01/02/03/03.5/04/05/07/09；bug 轨另加六件套）、diff 摘要、行号锚点、**交付面可达用户动线与出站出口清单（UI 变更不限 diff 面）**、明确未触碰面；**反锚定**——不附生产方的结论性摘要与自评（评审只看产物与契约，结论自产） |
| **P4 历史** | bugfix-log 同族条目、06-delivery FU、既有评审结论、ADR 与仓内约定 |
| **P5 专业** | 本环节批判清单（按 §3 能力矩阵），并说明"凭什么认为具备该能力" |
| **P6 独立** | 生产主体 / 评审主体、会话与模型分离要求、预算、高成本模型用户确认状态 |
| **P7 输出** | 发现分级 + 证据、缺口声明、结论、必带小节（评审 = §6 五节） |
| **P8 红线** | 不自签、未跑≠通过、超清单读盘须声明原因、合规事实不猜、不自行再派发子代理（需更深专项→结论中建议，编排者裁定） |

模板与门禁用五个标签承载同一契约（一一映射，不另立语义）：

| 标签（03.5 / 07 / E17 机校） | 契约组 |
|---|---|
| 项目背景 | P1 |
| 变更上下文 | P2 |
| 证据包 | P3 |
| 专业与历史 | P4 + P5 |
| 独立与成本 | P6 |

子 Agent 超出输入清单的读盘动作须在结论中声明原因；未携带项目背景的评审直接退回。主 Agent 用 `scripts/agent-gate dispatch <stage> <CHG>` 生成骨架（缺失项标 `[gap]`），不手写空 prompt。

**prompt 末位规则**：完成判据（P0）与红线（P8）置于派发 prompt 的**末尾**——长 prompt 注意力呈"中间塌陷、末端增强"（lost in the middle），关键判据沉到中部即事实性降权；装配顺序 P1–P6 在前、P7 次之、P8 与完成判据收尾。

### 2.1 分阶段派发骨架（每个环节 Agent 要干什么）

| 阶段 | 派发子代理 | 职责（要做到什么） | 必带输入 | 输出契约 |
|---|---|---|---|---|
| 勘探 | 只读勘探子代理 | 定位入口 / 调用链 / 现有约束，逐条给文件:行 | P0 P1 P3 P8 | 事实清单 + 证据行 + 未覆盖面 |
| 意图 | 业务 / 行业专家 | 澄清问题与业务现实，暴露隐藏假设 | P0 P1 P2 P4 | 问题陈述 + 未决问题 + 风险初判 |
| 规格 | 需求 Agent | REQ 可判定、编号连续、逐条挂靠 UJ | P0 P1 P2 P4 | 01-spec REQ 行 + 验收标准 |
| 影响 | 技术 / 架构专家 | 三维影响、爆炸半径、隐式链路 | P0 P2 P3 P4 | 02 三维 + 回滚策略 |
| 设计 | 架构 / 项管专家 | ≥2 候选选型、DES、WBS | P0 P2 P3 P4 | 03 + 03.5 |
| 测试计划 | 测试专家 | 十一维覆盖、SC 枚举、TC 落点 | P0 P2 P3 P5 | 04 用例矩阵 + TC 落点清单 |
| 编码 | 开发 Agent | 按 DES 实现，最小范围注释与 ReAct 三段 | P0 P2 P3 P8 | 04.5 记录 |
| 测试执行 | 测试 Agent | 真实命令输出与 rc，禁空口宣称 | P0 P3 P5 | 05 证据 + 未执行项清单 |
| 评审 | 独立评审子代理 | 批判性发现 + 证据，禁泛评 | P0–P7 全部 | 07 五节 + 发现处置 |
| 交付 | 交付 / 验收 Agent | DoD 逐条、RTVM 闭环、回滚终审 | P0 P2 P3 P7 | 06 / 09 + 结论 |

## 3. 专业能力矩阵

| 评审环节 | 必须具备的能力 | 判断要点（非穷举） |
|---|---|---|
| 架构评审 | 强推理、系统设计、演进性 | 边界与耦合、失败模式、容量与伸缩、可观测、回滚、与既有架构范式是否一致、是否先进合理、覆盖面与深度 |
| 代码评审 | 安全、性能、缺陷分析、业务合理性 | 注入/越权/敏感数据、并发与资源、性能红线、空值/异常/边界、业务语义是否成立、可维护性；变异抽查一条断言（临时变异验证测试真红后还原——自证测试非摆设） |
| UI 评审（`ui_change: true`） | UX、UE、可达性、业务合理性 | 用户任务闭环、信息架构、交互反馈、错误恢复、一致性、WCAG/可达性、真实业务场景 |
| 业务合理性终审 | 领域专家、业务现实 | 逐 UJ 质询成品行为在业务现实中是否成立；禁引本变更加工件作判定依据（§2.5 阶段 8） |
| 环节衔接评审 | 追踪矩阵、一致性 | 上游产物是否完整/自洽、下游是否具备开工条件、偏差与遗漏、返工风险 |
| 缺陷评审 | 根因分析、同族推演 | 最早未恢复失败点、排除其他假设、同族/邻接面、防回归 TC 覆盖 |
| 质量底线守护评审 | 质量度量判读、约束形态审查 | 底线数字有无与工具在位、diff 弱化五类（判据唯一权威=§8）、例外台账 owner+期限、底线只紧不松 |

## 4. 评审执行体与运行时适配（先探测目标仓，再选方案）

评审开始前必须探测**目标仓被打开的 Agent 客户端运行时**（即安装本 Skill 的项目当前使用的客户端，不是编辑 Skill 的源仓客户端），再选执行方案；禁止默认"一定用子 Agent"或"一定用外部 CLI"。

| 探测到的目标仓运行时协议族 | 建议评审执行方案 |
|---|---|
| `json-hooks`（如 `.claude/settings.json` / `.cursor/hooks.json` / `.agents/hooks.json` 等动态适配客户端） | 同客户端独立子 Agent + 独立会话；由动态生成的仓库级 Hook 负责遥测与停等检查；L2+ 换模型/厂商复核 |
| `plugin-api`（如 `opencode`） | 同客户端独立子 Agent + 独立会话；插件负责遥测；必要时用独立 CLI 进程起评审会话 |
| `git+ci`（经当前 Agent 自查确认无仓库级 Hook 能力） | 优先：外部独立 CLI（已安装者）起独立评审会话；次选：人类评审或 CI 独立 job；不得用同会话自评 |
| 多运行时共存 | 选能力/成本匹配的一个作评审执行体，其余仅作候选；不得同一模型既生产又评审 |
| 无可用独立执行体 | 显式阻塞：登记 FU/等待用户提供评审环境；不得降级为自评 |

探测命令：在**目标仓根**执行 `scripts/install-hook-adapter --detect`（按「当前进程环境 > 仓内配置 > PATH 回退」动态识别，不按固定产品名单写死，也不让 PATH 上的其他 CLI 抢占当前 Agent）；新客户端在安装/升级/首次触发 Skill 时通过 `scripts/install-hook-adapter --print-contract` 获取标准三事件契约动态生成接线并用 `--verify-wiring <file>` 自证。`scripts/agent-gate review-plan <变更号>` 会在目标仓根自动执行该探测，并把结果、所需专家、候选模型与成本档位一并输出。

## 5. 模型选择与成本确认

- 配置文件：仓库根 `.agent-review-models.json`（可选）。声明模型 `id/provider/cli/tier/strengths` 与角色 `min_tier`。
- 档位语义：`economy`（低）/`standard`（中）/`deep`（高）。`deep` 或配置 `approval: true` 的模型必须用户确认。
- 流程：`agent-gate review-plan <变更号>` 输出候选 → 用户选择 → 用户设置 `AGENT_REVIEW_MODEL_APPROVED=<model-id>`（或显式批准记录）→ 再次运行 `review-plan` 写入 `.agent-state/review-plan.json`。
- 禁止：AI 自行把档位从 economy 升到 deep；AI 以"效果更好"为由绕过用户确认；同模型同会话自评后补签名。

## 6. 评审输出契约

`07-review-report.md` 必须包含：

1. `## 评审输入契约与专业能力`：装载了哪些项目背景/历史教训、所需能力、批判性质询清单、AI 判断依据。
2. `## 模型选择与成本确认`：评审执行体（客户端/CLI）、模型、档位、候选清单、用户确认引用；未命中经济档写"未命中（经济档，无需确认）"。
3. `## 独立性声明（生产 vs 评审）`：生产主体与评审主体的 `平台/模型/会话` 三元组，逐项证明分离；L2+ 证明跨模型/厂商。
4. `## 发现处置`：逐条发现 + 严重度 + 证据 + 处置 + 来源；无发现写单行声明。**严重发现必须附具体修法**（改哪里、怎么改）——只给结论不给修法等同未评审。
5. `## 评审结论`：通过/有条件通过/退回；有条件通过必须列出整改项与闭环证据。

发现严重度判据（三档，枚举与 07 模板一致；缺陷化升级为 BUG 时按 bug 轨现行 `severity:` 口径重判登记，禁止为对齐新造词表）：

| 严重度 | 阻断交付 | 判定判据 | 处置动作 |
|---|---|---|---|
| 严重 | 是 | 数据丢失/安全漏洞/功能破坏/门禁红线 | 交付前必修，附具体修法；不得以 FU 代替 |
| 中 | 否（限期） | 缺测试、错误抽象、错误处理缺失 | 修复或登记 FU（负责人+期限） |
| 低 | 否 | 风格类（更简设计、命名、注释） | 作者裁量，不阻塞交付 |

**评审验证动作与补偿覆盖对账**：评审结论须能回答"本评审实际做了哪些独立验证"（跑过的命令、看过的面、查过的锚点）——未做的验证也须写明（如"未跑构建"）；禁"证据链完整"式背书。达标确认同理：确认达标必须指认参照物（`路径:行号`/编号对照）。当无浏览器工具面而走「工具面缺失 + 视觉证据包」补偿时，必须附覆盖对账（交付面全部可达出口/UJ vs 补偿包已提供路径 vs 未覆盖差集）；**未覆盖差集非空时严禁给 `PASS`（最高仅可给有条件通过）**。

## 7. 反模式（自我借口 vs 反驳，一律退回）

| 评审者的自我借口 | 反驳（现实） |
|---|---|
| "没发现问题=代码没问题" | 零发现零建议=泛评（§2.2 增量承诺），等同未评审；先自检是否真质疑过上游（07 上游错误计数全零=危险信号） |
| "同会话先实现再自评，效率高" | 生产与评审分离是铁律 1；自评=独立性造假 |
| "项目背景我大概知道，不用专门装载" | 未携带项目背景的评审直接退回（§2 契约）；脱离项目的模板泛评是噪声 |
| "模板勾选齐了就是评审过了" | 门禁只校结构/证据/独立性/成本确认；专业结论必须可追溯到证据，勾选不产生判断 |
| "高成本模型效果好，直接用了" | 档位升档必须用户确认（铁律 5）；未确认即用=门禁违规 |
| "结论与 05/01.5 矛盾，但差异不大" | 评审结论与 05 证据、01 RTVM、09 回填清单相互矛盾而不说明=07 无效；每处矛盾须显式解释或退回 |
| "这个发现我确信，不用给修法" | 严重发现必须附具体修法（§6）；只给结论不给修法=把返工成本转嫁给作者 |

## 8. 质量约束面（定义与守护）

- **定义动作**：首次变更或项目尚无质量底线时，架构＋项目管理专家在 00.5 沟通稿中提出**带数字的底线**（覆盖率/性能预算/变异分数/lint 严格度等；每个数字附工具与理由），落 P00「成功判据」既有节或 `.agent-governance.yml` 用户自由段；"质量要高"类无数字表述不算底线。gate 不读不校验该自由段——数字底线靠本面守护评审（B 层），测试弱化靠 E160（A 层）。
- **守护动作（测试弱化五类 diff-watch，gate E160 执法 A 层 + 评审复核 B 层）**：①断言被删除或弱化（期望值放宽、断言整行消失）；②测试被跳过或收窄（skip/only/条件恒真）；③阈值被下调（覆盖率/预算/超时）；④检查器被静默（disable/ignore 注释、规则移除）；⑤例外出现而无 owner+期限（豁免必须有负责人与到期日，到期即恢复执行）。gate 暂存面命中即拒（E160），owner+期限标注为唯一逃生口。
- **ratchet 方向**：底线只紧不松——收紧静默生效，放松必须显式；评审发现"悄悄放松"按严重发现处置。
