# 评审智能契约（Review Intelligence Contract）

> 文档编号：methodologies/review-intelligence.md（方法论层；随 `bootstrap --core` 下发）
> 定位：规范 §2.2 管"谁必须评审、独立性到哪一级"；本文件管"评审怎么带着项目背景、专业能力与批判性去判断，以及评审执行体/模型怎么选"。
> 唯一权威关系：风险分级与四主体互异仍以 §0.5 / §2.1 规则 10 为唯一权威；本文件不另立等级、不替代门禁。

## 0. 铁律（不可协商）

1. **生产与评审分离**：同一变更内，作者、实现、测试、评审四主体互异；评审不得与生产同会话、同执行主体，更不得自签。编排 Agent 不得兼任任一签署（§2.1 规则 10）。
2. **评审必须带项目背景**：评审前装载项目快览、P12 领域上下文、P01–P04 相关章节、bugfix-log 同族教训、FU 台账与本变更产物；禁止脱离项目实际做模板泛评。
3. **评审必须专业对口**：架构评审看架构先进性与覆盖面；代码评审看安全、漏洞、性能、缺陷与业务合理性；UI 变更另看 UX/UE 与可达性。能力不匹配的评审视为无效。
4. **评审必须批判**：至少给出 1 条有证据的发现或显式达标确认，并给出 1 条可执行改进；零发现零建议 = 泛评，退回（§2.2 增量承诺）。
5. **高成本模型必须用户确认**：AI 只能列出候选、能力与成本档位，不得自行选择高成本模型；用户确认后才可进入评审。未确认即用高成本档 = 门禁违规。

## 1. AI 判断原则（不写死）

- 门禁只校验**结构、证据、独立性、成本确认**；专业结论由评审 AI 基于证据判断，禁止用固定分数/固定关键词替代判断。
- 每个判断必须可追溯到证据：`路径:行号`、REQ/DES/TC 编号、日志片段、项目背景条目或 bugfix-log 教训。
- 评审 AI 可以推翻引擎建议/前序结论，但必须在 `07-review-report.md` 写明「推翻对象 + 证据 + 复核主体」；无证据的推翻无效。
- 自适应判定（测试选节、预算、换挡、是否加严）由 AI 给出判断与依据，引擎建议只作输入；判断记录落 `00-intent.md`「AI 判断记录」或 09「重要上下文」。

## 2. 评审派发输入契约（主 Agent 必须供给）

派发评审子 Agent / 外部评审 CLI 时，prompt 必须包含：

| 输入 | 必含内容 |
|---|---|
| 项目背景 | 项目速览、P12 领域域/行业约束、P01–P04 相关章节结论、系统特点与关键链路 |
| 变更上下文 | 变更号、风险等级、`ui_change`、变更文件清单、diff 摘要、受影响 REQ/DES/TC |
| 待核对产物 | 01/02/03/03.5/04/05/07/09 路径 + 行号锚点；缺陷六件套路径（bug 轨） |
| 历史教训 | bugfix-log 同族条目、06-delivery FU、既有评审结论 |
| 专业能力 | 本环节需要的专家能力（见 §3）与禁止越权范围 |
| 独立性约束 | 生产主体标识、评审主体标识、会话/模型/厂商分离要求 |
| 成本约束 | 候选模型/CLI、成本档位、用户确认状态 |

子 Agent 超出输入清单的读盘动作须在结论中声明原因；未携带项目背景的评审直接退回。

## 3. 专业能力矩阵

| 评审环节 | 必须具备的能力 | 判断要点（非穷举） |
|---|---|---|
| 架构评审 | 强推理、系统设计、演进性 | 边界与耦合、失败模式、容量与伸缩、可观测、回滚、与既有架构范式是否一致、是否先进合理、覆盖面与深度 |
| 代码评审 | 安全、性能、缺陷分析、业务合理性 | 注入/越权/敏感数据、并发与资源、性能红线、空值/异常/边界、业务语义是否成立、可维护性 |
| UI 评审（`ui_change: true`） | UX、UE、可达性、业务合理性 | 用户任务闭环、信息架构、交互反馈、错误恢复、一致性、WCAG/可达性、真实业务场景 |
| 业务合理性终审 | 领域专家、业务现实 | 逐 UJ 质询成品行为在业务现实中是否成立；禁引本变更加工件作判定依据（§2.5 阶段 8） |
| 环节衔接评审 | 追踪矩阵、一致性 | 上游产物是否完整/自洽、下游是否具备开工条件、偏差与遗漏、返工风险 |
| 缺陷评审 | 根因分析、同族推演 | 最早未恢复失败点、排除其他假设、同族/邻接面、防回归 TC 覆盖 |

## 4. 评审执行体与运行时适配（先探测目标仓，再选方案）

评审开始前必须探测**目标仓被打开的 Agent 客户端运行时**（即安装本 Skill 的项目当前使用的客户端，不是编辑 Skill 的源仓客户端），再选执行方案；禁止默认"一定用子 Agent"或"一定用外部 CLI"。

| 探测到的目标仓运行时 | 建议评审执行方案 |
|---|---|
| `claude` / `cursor`（json-hooks） | 同客户端独立子 Agent + 独立会话；hook 负责遥测与停等检查；L2+ 换模型/厂商复核 |
| `opencode`（plugin-api） | 同客户端独立子 Agent + 独立会话；插件负责遥测；必要时用 `opencode run` 起独立评审进程 |
| `gemini` / `codex`（git+ci，无仓级 hook） | 优先：外部独立 CLI（`claude` / `codex` / `opencode` 等已安装者）起独立评审会话；次选：人类评审或 CI 独立 job；不得用同会话自评 |
| 多运行时共存 | 选能力/成本匹配的一个作评审执行体，其余仅作候选；不得同一模型既生产又评审 |
| 无可用独立执行体 | 显式阻塞：登记 FU/等待用户提供评审环境；不得降级为自评 |

探测命令：在**目标仓根**执行 `scripts/install-hook-adapter --detect`（只读，输出 runtime/family/layers）——它读的是目标仓的 `.claude/` / `.opencode/` / `.cursor/` 等客户端配置，不是源仓。`scripts/agent-gate review-plan <变更号>` 会在目标仓根自动执行该探测，并把结果、所需专家、候选模型与成本档位一并输出。

## 5. 模型选择与成本确认

- 配置文件：仓库根 `.agent-review-models.json`（可选）。声明模型 `id/provider/cli/tier/strengths` 与角色 `min_tier`。
- 档位语义：`economy`（低）/`standard`（中）/`deep`（高）。`deep` 或配置 `approval: true` 的模型必须用户确认。
- 流程：`agent-gate review-plan <变更号>` 输出候选 → 用户选择 → 用户设置 `AGENT_REVIEW_MODEL_APPROVED=<model-id>`（或显式批准记录）→ 再次运行 `review-plan` 写入 `.agent-state/review-plan.json`。
- 禁止：AI 自行把档位从 economy 升到 deep；AI 以"效果更好"为由绕过用户确认；同模型同会话自评后补签名。

## 6. 评审输出契约

`07-review-report.md` 必须包含：

1. `## 评审输入契约与专业能力`：装载了哪些项目背景/历史教训、所需能力、批判性质询清单、AI 判断依据。
2. `## 模型选择与成本确认`：评审执行体（客户端/CLI）、模型、档位、候选清单、用户确认引用；未命中经济档写"未命中（经济档，无需确认）"。
3. `## 独立性声明（生产 vs 评审）`：生产主体与评审主体的 `平台/模型/会话` 三元组，逐项证明分离；L2+ 证明跨模型/厂商。
4. `## 发现处置`：逐条发现 + 严重度 + 证据 + 处置 + 来源；无发现写单行声明。
5. `## 评审结论`：通过/有条件通过/退回；有条件通过必须列出整改项与闭环证据。

## 7. 反模式（一律退回）

- 同一会话/同一模型先实现再自评，或编排 Agent 代签。
- 只写"已按规范评审/未发现问题"而无证据、无项目背景引用。
- 用模板勾选代替判断；用固定阈值代替专业评估。
- 未探测运行时就直接假定执行体；未告知成本就选用高成本模型。
- 评审结论与 05 证据、01 RTVM、09 回填清单相互矛盾而不说明。
