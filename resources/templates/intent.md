# 00-intent.md - 变更意图（Intent）

> 本文档是变更管线的**起点**：在任何需求/设计/编码动作之前，先用非技术语言记录"为什么启动这次变更"。
> 它允许由非工程师（业务方、运维值班、监控系统自动注入）创建与填写，是事故自动重入管线的标准入口（规范 §2.17）。
> **更新语义：追加式**（§2.15）--意图澄清过程按节追加，禁止覆盖历史表述。
> 填写完成后，由需求角色转写为 `01-spec.md` 的 `REQ-xxx`（正式需求规格），本文件保留为原始意图凭据。

- 变更编号：`CHG-xxx` / `BUG-xxx`
- 提出人 / 来源：<人类角色 / 工单链接 / 告警系统名称>
- 创建时间：<YYYY-MM-DD HH:mm TZ>
- 风险等级初判：<L0-L3（正式判定以 00-governance.json 为准，§0.5）>

## 1. 问题（Problem）

[必填] 用非技术语言描述观察到的现象、痛点或告警；引用具体事实（发生时间、指标数值、影响面、频率），禁止"系统不太好用了"这类不可验证描述。

## 2. 预期结果（Expected Outcome）

[必填] 变更完成后，用户 / 系统 / 指标应当呈现的**可验证**状态（示例：错误率从 X% 降至 Y% 以下）。

## 3. 受影响用户与系统（Affected Users & Systems）

[必填] 谁受影响、影响频次与严重度；初步涉及的系统与链路。不确定时写"待影响分析（02-code-impact-analysis.md）确认"。

## 4. 约束（Constraints）

[必填] 时间窗、合规 / 安全约束、成本预算（如 LLM token 量级）、明确不做的范围（Out of Scope）。

## 5. 开放问题（Open Questions）

[必填] 启动时尚未澄清的问题、澄清责任人与期限；**全部关闭前不得进入阶段 3 方案设计**（规范 §2.5）。
