# 方法论选型总纲（Methodology Selection Guide）

> **定位**：本文件是全部方法论的**选型入口与分级权威表**——回答"这个变更允许用哪些方法论、禁止用哪些、为什么"。任何设计/编码/测试决策在给出"为什么用"之前，必须先对照本表；本表未收录的方法论，视为 M3 受限级处理。
> **权威关系**：本文件不复制 `docs/DEVELOPMENT_STANDARDS.md` 的任何门禁要求；二者冲突时以规范为准。本文件只做一件事——把"合适的方法论优先"变成可查表、可审计的决策。
> **强制范围**：阶段 2 影响分析（§2.5）与阶段 3 技术选型必须引用本表；阶段 5 实现须遵守已选方法论的详情文档（`docs/methodologies/` 目录）。

---

## 1. 使用方式（Agent 与人类通用）

1. **查阶段**：定位本次变更所处的主要阶段（阶段 1–10，见规范 §2.5）。
2. **查表分级**：在 §3 主表中找到候选方法论，确认其 M0–M3 分级与适用条件、不适用场景。
3. **对照风险等级**：结合 §0.5 风险分级（L0–L3）核对 §4 联动约束。
4. **记录选型**：把"选了什么 / 为什么用 / 为什么不用落选项"写入 `docs/<feature>/03-modification-plan.md` 的「技术选型与决策记录」节（规范阶段 3 已强制 ≥2 候选对比；本表是该对比的**评分依据**，不替代对比本身）。

> 本文件**不新增机器门禁**：`agent-gate` 与 CI 不校验本表（预留 v3.x 评估，见规范 §2.14）。选型正确性由阶段 3 的 B 层验收（计划 Agent 双视角核对，规范 §2.5）与阶段 8 Review 把关。

## 2. 方法论分级定义（M0–M3）

| 分级 | 名称 | 含义 | 启用要求 | 跳过要求 |
|---|---|---|---|---|
| **M0** | 强制基线 | 任何变更默认适用；构成工程质量的下限 | 无条件适用 | 跳过须在 03 选型记录中显式标注"不适用，理由"（与规范 §2.16.6 禁止静默裁剪同精神） |
| **M1** | 默认推荐 | 适用场景下的默认选择；不用不会立即违规，但会积累债 | 适用即默认采用 | 不用须在 03 选型记录说明理由 |
| **M2** | 条件启用 | 仅命中触发条件才启用；启用即产生长期维护成本 | 命中触发条件 + 03 记录"为什么用"（含落选项对比） | 未命中条件而启用 = 过度设计，Review 退回 |
| **M3** | 重量级/受限 | 引入成本高（人力/流程/认知），误用代价大 | 触发条件 + 风险等级 ≥L2 + 独立角色论证（B 层）+ 决策入 ADR | 未满足前置条件即启用 = 严重过度设计，Review 直接退回 |

**分级与风险等级的关系**：M0/M1 随任何风险等级生效；M2 启用须在 03 记录论证；M3 仅 L2/L3 变更可启用（L0/L1 启用 M3 一律视为过度设计）。

**违规判定（唯一权威，详情文档一律引用本条，不另行定义）**：M0 条目违反 = 🔴 严重（如弱类型穿层、吞异常）；M1 条目违反 = 🟡 中；M2/M3 未命中触发条件即启用（过度设计）= 🔴 严重，Review 退回。判定结果记入 `07-review-report.md` 问题分级。

## 3. 主表：阶段 × 方法论 × 适用条件 × 不适用场景

> "规范已强制"的方法论列在表内以 M0 呈现并标注出处，保持单一权威源（规范正文）；本表对它们只做**汇总路由**，不复制其要求。

### 3.1 阶段 1：需求与规格定义

| 方法论 | 分级 | 适用条件 | 不适用场景 | 详情 |

| 用户故事 + 验收标准（DoD） | M0（规范门禁 1 已强制） | 所有需求变更 | 无（跳过即违反门禁 1） | 规范 §2.5 阶段 1 |
| 输入输出契约（字段级定义） | M0（规范已强制） | 所有需求变更 | 无（LLM 链路额外叠加 data-structures.md §4） | 规范 §2.5 阶段 1；`docs/methodologies/data-structures.md` |

| 方法论 | 分级 | 适用条件 | 不适用场景 | 详情 |
|---|---|---|---|---|

## 4. 风险等级联动速查（L1 判定示例）

**问题：L1 的一次简单 CRUD 接口开发，允许用哪些、禁止用哪些？**

| 判定 | 方法论 | 依据 |
|---|---|---|
| 允许（必须） | 用户故事+DoD、输入输出契约、三维影响分析、≥2 候选对比、类型化数据建模、TDD、九类覆盖维度、KISS/YAGNI、防御式编程、全量回归、双视角审查 | 全部 M0，规范已强制 |
| 允许（默认推荐） | SOLID/DRY（逐条按需）、ADR（若该接口决策会影响其他模块）、测试金字塔（若仓库已分层） | M1，不用须在 03 说明 |
| 允许（须论证） | 表驱动（≥3 同构分支时）、契约测试（有第二消费方时）、领域术语表 | M2，须命中触发条件并记录 |
| **禁止**（未满足前置条件即启用 = 过度设计，Review 退回） | DDD 战术设计（无复杂领域规则）、C4 全套（单模块变更）、ATAM（非关键路径架构）、事件风暴（CRUD 需求）、设计模式套用（变化点 <3） | M3/M2 未命中条件 |

**反例判定**：一个 L1 CRUD 若出现 Builder + 抽象工厂 + 三层接口继承 + 独立领域服务层，按本表应**直接否决**——每一层抽象都没有对应的触发条件（变化点 <3、无跨实体不变量）。判否依据记入 07-review-report.md 问题分级（严重，统一规则见 §2）。

## 5. LLM 链路叠加约束（联动规范 §2.9）

涉及 LLM 调用的变更，选型分级仍按 §3 各表；结构细则不在此重复，唯一落点：
- 输入输出结构分离 / 输出 schema 版本化 / 降级结构显式建模 → `docs/methodologies/data-structures.md` §4；
- 模型调用错误分类（可重试 / 不可重试 / 需降级）→ `docs/methodologies/development.md` §3.4（联动规范 §2.9.3）。

## 6. 维护规则（本表如何演进）

- **入表条件**：新方法论必须同时具备"适用条件"与"不适用场景"两列——写不出不适用场景的方法论（万金油）不许入表。
- **入表流程**：走规范 §2.14 标准升级（版本号 + 升级日志行），禁止静默加行。
- **详情文档解耦**：本表只管分级与路由；方法论落地细则放 `docs/methodologies/<name>.md`，每篇独立文件、几百行以内，AGENTS.md 只做路由指针。
- **反向检查义务**：每个 M2/M3 方法论的详情文档必须含"反向检查"节（用真实场景验证它不会被无脑套用）；本表 §4 即 L1 CRUD 的反向检查样例。

## 7. 暂缓项（明确不做，防提前过度设计）

以下方法论**本版不提供详情文档**，仅受本表 M3 分级约束：DDD 战术设计、C4 架构模型、ATAM 架构评估、事件风暴。启动条件：对应场景在真实变更中出现 ≥2 次且 M0–M2 方法论确已不够用，再走 §2.14 升级评估。Router/Schema 化的机器校验（自动拦截越级选型）同样暂缓。
