# 全局软件开发与变更规范（Development & Skills Standards）

> **【强制执行】本文件是项目全局最高开发规范**，适用于所有 AI Agent（Antigravity、Gemini、Claude、Cursor、Windsurf、Qoder 等）以及人类开发者。  
> **核心原则：文档先行、测试先行、全链路追踪矩阵映射、多 Skill 交叉验证、角色独立验证、按风险分级执行、逐项核对不遗漏。严禁无文档改代码，严禁未跑测试宣称完工，严禁同一执行主体自测、自审、自批，严禁用摘要/口头总结代替逐项清单核对（§2.16.6）。**
> **文档结构说明**：判定类内容（DoD/自检/风险分级/独立性/阶段验收）全文**只有一处权威定义**（§0.5、§2.16.3、§2.16.4、§2.5 总则），其余为强制引用；不一致时以权威章节为准。

## 0. 五大核心硬性约束与阻塞门禁（Hard Quality Gates）

任何变更任务若未通过以下 5 道门禁，**一律禁止合入主分支或标记为完成**：

```ini
       [ 门禁 1: 需求/设计先行 ]
       需求有变/新需求 ──► 必须先更新 01-spec & 03-plan ──► 严禁直接改代码
               │
               ▼
       [ 门禁 2: 测试脚本先行 ]
       编写/修改代码前 ──► 必须在 04-test-scripts 编写 TC ──► TDD 红绿循环
               │
               ▼
       [ 门禁 3: 运行测试与证据闭环 ]
       宣称完工前 ──────► 必须命令行跑测试并截取关键输出 ──► 严禁口头声明成功
               │
               ▼
       [ 门禁 4: 全链路追踪矩阵闭环 ]
       提交变更时 ──────► 必须在 09-changelog 闭环 RTVM ──► REQ ↔ DES ↔ CODE ↔ TC
               │
               ▼
       [ 门禁 5: 独立验证与合入授权 ]
       合入/发布前 ──────► 测试与审查由独立角色完成并留痕 ──► 禁止作者自证、自批
```

### 门禁 1：需求与设计先行门禁（Doc-First Gate）

- **约束规则**：只要涉及业务逻辑调整、接口字段增删、行为策略变更，**严禁直接修改代码**。
- **强制动作**：
   1. 必须先在 `docs/<feature>/01-spec.md` 更新需求规格，分配/更新需求编号（如 `REQ-101`）。
   2. 在 `docs/<feature>/03-modification-plan.md` 中更新技术方案与设计决策（如 `DES-101`）。
   3. 确认影响范围与向下兼容性后，方可启动代码编写。

### 门禁 2：测试用例先行门禁（Test-First Gate）

- **约束规则**：禁止“先写完代码，上线前补个测试”或“完全不写测试”。
- **强制动作**：
   1. 必须在 `docs/<feature>/04-test-scripts.md` 明确对应的测试用例编号（如 `TC-101`）。
   2. 测试用例必须覆盖：**正常流（Happy Path）+ 边界值/空值 + 异常兜底流**（最低下限；全维度按 §2.5 阶段 4 覆盖维度矩阵逐维执行）。
   3. 遵循 TDD 理念：先写出能复现问题或验证新特性的测试脚本（Red），再编写实现代码（Green）。

- **变更测试策略（复用 vs 新增判定）**：
   - **新增**功能/新分支/新字段/新调用点打点 → **必须新增 TC**（覆盖正常+边界+异常兜底，§2.5 阶段 4）。
   - **修改**既有逻辑（行为变化）→ 复用既有 TC 全量回归；对新增分支/边界须**扩展断言或新增用例**。
   - **纯重构**（行为不变）→ 复用既有 TC 全量回归，可不新增；若重构暴露新边界，补用例。
   - **删除**逻辑 → 删除对应 TC 须在 `09-changelog.md` 记录，禁止静默删。
   - **断言完整性**：修改的调用点打点（如可观测记录）必须**断言其内容**（执行≠覆盖），禁止只"跑到"不断言。
   - **全量回归强制**：任何代码变更合入前必须跑全量测试套件（如 `mvn -pl <module> -am test`），禁止只跑受影响用例（防副作用/回归盲区）。

### 门禁 3：完工证据验证门禁（Evidence-Before-Assertions Gate）

- **约束规则**：严禁在未实际执行测试并取得控制台输出的情况下宣称“已修复”、“已完成”或“测试通过”。
- **强制动作**：
   1. 必须在终端真实执行测试命令（如 `mvn test ...`）。
   2. 在 `05-test-results.md` 记录**脱敏后的**命令、耗时、退出码、Tests run / Failures / Errors 与原始日志制品链接；原始日志只可存放在受访问控制的制品库，禁止将敏感用户数据、密钥或 token 复制进 Git 文档。
   3. 若因外部环境受阻无法自动化运行，必须提供可执行的手动验证复现命令或接口测试用例。
   4. **批次保留（禁止覆盖历史批次）**：每次变更在 `05-test-results.md` **追加独立批次小节**（`## §N：CHG-XXX`），保留历史批次原文与状态（PASS/FAIL 不改写）；全量重跑给"本次总数 + 与上批对比"；增量补强记当批或新批次，不并入旧批次；修订历史错误加「修订说明」，禁止静默覆盖。

### 门禁 4：四维全链路追踪矩阵闭环门禁（Traceability Gate）

- **约束规则**：每一处代码改动都必须能向上追溯到需求，向下映射到测试；禁止无需求的“游离代码”，禁止无测试的“盲区代码”。
- **强制动作**：每次变更必须在 Changelog 中维护 **RTVM 追踪矩阵映射**（§4，短引用），并**回填所属功能的独立 RTVM 矩阵文件 `docs/<feature>/01.5-rtvm-matrix.md`**（§1.2：REQ→DES→TASK→TC 四维链路 + 验证状态）；只更新 changelog 不回填独立矩阵文件视为未闭环（四维链路断环亦然）。**v3.35.0 起本门禁同时执法项目总册回填**：09 CHG 必含「项目总册回填清单」节，P00–P11 逐册勾选或标"未命中"（§1.3；gate stop/CI 逐册机校），被更新章节留变更注记。

### 门禁 5：独立验证与合入授权门禁（Independent Verification Gate）

- **约束规则**：开发者（人或 Agent）不得批准自己实现的测试结论、代码审查结论、合入或发布；“使用多个 Skill”不等同于独立验证。
- **强制动作**：测试验证和代码审查须由与开发角色不同的执行主体完成，并在 `07-review-report.md` 与 `09-changelog.md` 记录角色、执行主体、输入基线（commit SHA/文档版本）、结论与时间。
- **高风险变更**：涉及敏感用户数据（PII）、认证授权、生产 DB、模型/Prompt、对外接口破坏性变更或 P0 热修复时，除独立测试与 Review 外，必须由有授权的人类 Release Owner/领域负责人明确批准；Agent 不得替代该授权。

## 0.5 变更风险分级矩阵（唯一权威判定源）

> **强制规则**：全文任何提及"低风险""高风险""可合并角色""可豁免"之处，**一律以本节分级为唯一依据**，禁止 Agent 自行解释或另立标准。Agent 在任务开始时必须先在此表中判定风险等级，并把判定结果与依据写入 `09-changelog.md`「重要上下文」字段（§2.16.1 前置核对的一部分），作为后续角色独立性、平台/模型要求是否达标的判定基线。**未记录风险等级判定的变更，视为按 L3（最高等级）执行，不得自行降级。**

### 0.5.1 风险等级判定表

| 等级 | 判定依据（命中任一即为该级，就高不就低） | 典型场景 |
|---|---|---|
| **L0 极低** | 无逻辑变更：纯文档、注释、格式化、日志文案微调 | 修正错别字、调整代码缩进、补充注释 |
| **L1 低** | 需求优先级 P2，且不涉及核心业务模块、不涉及对外接口、不涉及§0门禁5高风险清单 | 内部工具函数优化、非核心页面样式调整 |
| **L2 中**（默认档） | 需求优先级 P0/P1，涉及核心业务逻辑，但未命中 §0 门禁5 高风险清单 | 常规功能新增/修改、内部服务间接口调整 |
| **L3 高** | 命中 §0 门禁5 高风险清单任一项：敏感用户数据（PII）、认证授权、生产 DB、模型/Prompt、对外接口破坏性变更、P0 热修复 | 核心业务逻辑变更、鉴权改动、生产数据订正、prompt 变更、对外 API 破坏性升级 |

### 0.5.2 风险等级 × Agent 独立性与平台要求矩阵

> 呼应 §2.1 Agent 角色分工：本表把"跨工具/跨模型厂商交叉验证"从可选实践，明确为按风险分级的**强制要求**，防止"同一 AI 厂商不同马甲互相验证"规避门禁 5 的实质。

| 等级 | 需求/计划角色 | 开发 Agent | 测试 Agent | Review Agent | 平台/模型要求 | 人类介入 |
|---|---|---|---|---|---|---|
| L0 | 可与开发合并 | Agent A | 可与开发合并（仅需留痕） | 评审不可与作者/开发合并（§2.1 规则 10 最低线） | 无强制要求 | 无 |
| L1 | 可与开发合并 | Agent A | 必须独立子任务上下文（可同平台） | 必须独立子任务上下文（可同平台） | 无强制跨平台要求 | 无 |
| L2（默认） | 独立角色 | Agent A | 独立执行主体 + 独立子任务上下文（不同会话） | 独立执行主体 + 独立子任务上下文（不同会话） | 建议至少 1 环节跨平台/跨模型厂商（如开发用 Claude Code、Review 用 Codex） | 无（除非触发 §5 例外流程） |
| L3（高风险） | 独立角色 | Agent A | **必须**跨平台/跨模型厂商的独立 Agent | **必须**跨平台/跨模型厂商的独立 Agent，且与测试 Agent 所用平台/模型不同 | **强制**：开发、测试、Review 三方中至少覆盖 2 个不同底层模型厂商/平台 | **强制**：Release Owner 或领域负责人书面授权，Agent 不得替代（§0 门禁5） |

- **降级判定禁令**：L2/L3 变更不得以"任务简单""改动很小"为由自行降级到 L0/L1；如实际执行后发现风险等级判定有误，须在 changelog 中显式记录"风险等级修订"并说明理由，不得静默改判。
- **L0/L1 按轻量通道执行（v3.23.0）**：判为 L0/L1 的变更**应当**按 §1.1「L0/L1 轻量通道」裁剪表达成本（四件单行"未命中，不适用"声明 + 同日多变更落批次目录）——反向违规同降级禁令同类：把 L3 级全套仪式套在 L0/L1 变更上、无谓放大成本，亦属执行偏差（§5 反模式）。
- **平台/模型证据格式**：凡命中"跨平台/跨模型厂商"要求的环节，角色签署表（§4）「执行主体/Agent 标识」字段必须按 §2.1.7 格式填写，缺失或格式不合规视为独立性证据不足，门禁 5 不通过。
- **专家独立性归属（v3.34.0）**：§2.2 分阶段专家矩阵的独立性判定一律以本表为唯一权威——专家是既有角色的细分执行主体，其签署权映射回本表对应角色列，不得在 §2.2 另立等级或豁免标准。

## 1. 四维端到端需求追踪矩阵（RTVM 规范）

为确保“需求 -> 设计 -> 代码 -> 测试”环环相扣，项目统一使用以下编号规范与映射矩阵：

### 1.1 统一编号规范

**本表为全项目唯一编号权威源**：以下 11 种前缀此前分散定义在 §1、§2.6、§2.12、阶段 6 等多处，现统一归并于此；其余章节一律只引用本表，禁止另行定义新前缀或重复描述规则。

| 维度 | 标识前缀 | 说明 | 所在文档 |
|---|---|---|---|
| **需求规格 (Requirement)** | `REQ-xxx` | 业务需求、用户故事、功能约束 | `01-spec.md` |

### 1.2 独立 RTVM 矩阵文件与编号顺序规范

**每个功能必须生成独立 RTVM 矩阵文件 `docs/<feature>/01.5-rtvm-matrix.md`**（带文档编号，独立成 md，不内嵌于其他文档）：

- **四维链路（一环一环）**：RTVM 从 **需求 → 设计 → 任务 → 测试** 四个维度逐环跟踪，一环对应一环——每个 REQ 必须能顺链走到 DES → TASK → TC，中间不可断环（设计须落到任务、任务须产出测试）。
- **矩阵表**：一张完整表汇总该功能**全部** REQ，列 = 需求编号 (REQ) / 需求简述 / 设计编号 (DES) / 核心设计方案 / 任务编号 (TASK) / 代码实现 (CHG/位置) / 测试用例 (TC) / 测试方法 / 验证状态（与 changelog §4 追踪矩阵映射列对齐）。
- **回填规则**：每次 CHG 完成后必须回填该文件的对应 REQ 行（TASK、CHG、TC、验证状态），禁止只更新 changelog 而不同步 `01.5-rtvm-matrix.md`（未闭环，§5 拦截）。
- **编号顺序规则（强制）**：
   1. 各类编号（REQ/DES/TASK/CHG/TC/SC/BUG/CFG/DB/FU）各自**连续递增分配、不得跳号、不得重号**；
   2. **历史已分配编号不重排**（新编号只能继续递增，禁止为美观重排既有编号）；
   3. 矩阵表行**按 REQ 编号升序**排列；同一 REQ 多个 DES/TASK/CHG/TC 用 `/` 分隔，顺序 = 设计→任务→变更→测试（四维链路）。
   4. 需求若被后续 CHG 拆分/补充（如 CHG-006 新增 REQ-001~003 属于既有功能），新 REQ 继续递增，不并入旧编号。

- **扩展维度**：当变更涉及配置/DB（见 §2.6），在 `01.5-rtvm-matrix.md` 内追加第五维度映射子表（`CFG-xxx`/`DB-xxx` ↔ REQ ↔ DES ↔ CHG ↔ TC，模板见 §2.6.3），`06.5-deployment-config.md` 保留明细。

矩阵表模板（写入 `docs/<feature>/01.5-rtvm-matrix.md`）：

## 2. 全局 Skill 交叉验证矩阵（Cross-Validation Matrix）

在软件生命周期的每个阶段，必须激活对应的 **核心技能组合（每个阶段 ≥ 2 个）** 进行交叉制衡与闭环：

### 2.1 Agent 角色分工、子 Agent 调度与独立性

> **Skill 是能力组合，Agent/人是责任主体；二者不得混淆。** 可使用 Cursor、Codex、Claude Code、Gemini 或人类开发者，平台名称不是独立性的证明。独立性以“不同执行主体 + 独立任务上下文 + 未修改被验证产物”为准。

**子 Agent 规则（强制，AI 执行时逐条自查，不得跳过任一条）**：

1. 编排 Agent 按"需求/计划、开发、测试、Review"分派子任务，分派前依 §0.5 定级；角色合并与跨平台一律按 §0.5.2 矩阵，**禁止编排 Agent 自行合并角色**。
2. 测试 Agent 必须先基于 `REQ/DES/TC` 和接口契约制定或审查测试，再读取实现；不得仅按开发 Agent 提供的实现说明写测试。
3. Review Agent 必须检查 diff、RTVM、测试证据和未动项，并使用独立上下文形成结论；不得只转述开发 Agent 的结论。
4. **独立性最低要求**：不同 Agent 至少不同会话/子任务上下文、不同执行主体标识；L2/L3 跨平台要求见 §0.5.2，不得以同工具不同子 Agent 替代；平台无法保证独立上下文时改由人类或另一平台复核。
5. 每个 CHG 在 `09-changelog.md` 记录角色签署表（§4 模板）。无独立性证据，门禁 5 不通过。
6. Agent 仅可使用任务所需的最小权限；不得读取、输出或写入生产密钥/敏感用户数据。工具调用、测试命令和批准结论须可审计。
7. **Agent 标识强制格式**：角色签署表「执行主体/Agent 标识」字段必须填写 `平台名/模型标识 + 会话或任务ID`（示例：`Claude Code / claude-sonnet-4-6 / task-8f21`）。仅填"AI""Agent"或留空，一律视为独立性证据不足，门禁 5 判定为不通过，任务打回编排 Agent 重新指派。
8. **分歧升级机制**：测试 Agent 或 Review Agent 对同一 CHG 连续 2 次退回仍未达成一致时，编排 Agent 必须停止重复分派，转为升级人类介入仲裁（不得由编排 Agent 自行裁决对错）；仲裁过程与结论记入 `07-review-report.md`，并同步在 `09-changelog.md`「重要上下文」注明升级原因。
9. **完成状态原子化**：未产出本节"必须交付/签署"物前不得标记环节"完成"；编排 Agent 汇总时逐环节核对交付物存在性（不采信口头汇报），方式见 §2.16.6。
10. **角色单一职责（v3.34.0，一人一角色）**：同一 CHG 内**作者、实现、测试、评审**四主体 §2.1.7 标识互异（L2+ 四互异；`00-governance.json` 声明 `spec_author`——填 01-spec 作者（需求 Agent）标识，03 方案作者核对走签署表"方案评审"行；签署表核对）；**最低线适用于全部等级**：评审独立且作者≠评审（L0/L1 的其余合并按 §0.5.2 矩阵留痕）；生产批/评审批按 §2.2 两批制；编排 Agent 不得兼任任一签署；同标识无豁免＝门禁 5 不通过，打回重派。

## 2.5 分阶段产物与规格（Stage Deliverables & Specs）

> 每个阶段必须产出**明确产物**，且产物内容必须达到本节约定的**规格下限**（必含清单），未达规格不得进入下一阶段（对应 §3 检查清单）。所有产物命名统一放于 `docs/<feature>/` 目录，编号规则见 §1.1；启用变更管线/门禁的仓库，管线入口件与必检产物按 §2.17「产物目录双轨约定」落变更目录 `docs/changes/<变更号>/`。

### 阶段产物验收标准总则（唯一权威定义，v2.19.0 起）

> 每个阶段的产物除满足"必含清单"（规格下限）外，必须通过该阶段正文「验收标准」行的**两层验收**；各阶段「验收标准」行为该阶段验收的**唯一权威定义**，其余章节只引用不另立。任一层未过，不得进入下一阶段：
>
> - **A 层（机器可验）**：结构标记类硬证据（编号体系、必含节、绑定标记）。可由 `scripts/agent-gate`（begin/pre-write/stop 门禁内置 A 层校验）或 CI（`check-standards-compliance.sh`）确定性校验。**AI 在声明该阶段完成前，必须先自行执行对应校验命令（见下方速查表），并把命令与关键输出记入 09「变更执行检查清单」——只口头宣称"通过"而不附命令记录，视为未验收（§5 拦截）。**
> - **B 层（角色判定）**：质量与正确性判断项，由对应独立角色（测试 Agent / Review Agent，§2.1/§0.5.2）逐条核对并勾选、留 Agent 标识（§2.1.7）；**开发 Agent 不得自评 B 层通过**。
> - **勾选格式与落点**：每个阶段"声明完成"前，AI 必须按 §2.16.6 第 1 条**逐项引用该阶段验收标准条目号并勾选** `[x]`/`[ ]`（不要求抄录原文），随 §3 清单归档 `09-changelog.md`「变更执行检查清单」；只写"已验收 / 已按规范产出"而不逐项引用列出，视为未验收，该阶段判定为未完成（§5 拦截）。
>
> **表达成本条款（v3.24.0）**：
> - **跨产物引用制**：根因 / 影响以 `02-code-impact-analysis.md` 为唯一权威，`00-intent.md` / `09-changelog.md` 一行索引引用（"见 02 §业务影响"），禁止跨产物复制长文（同 §4 短引用制）。
> - **单产物软上限**：变更目录单产物默认 ≤40 行（`05-test-results.md` / `09-changelog.md` 累积型豁免）；超行须头部一行说明理由，无理由按 B 层未过。只裁表达冗余，**不裁必含清单规格下限**。超行的典型合法承载 = 02 / 04（实证内容）。
> - **产物最小表达形态（v3.25.0）**：`00-intent.md` 3-5 行摘要 + "详见 02"（gate 硬校验节「预期结果 / 开放问题」必须保留）；`03` 候选对比每案 ≤2 行（保 DES 编号 + "选型/备选"关键字，gate A 层兼容）；`03.5` 免拆时单行声明 + 里程碑两行；验收框先 `[ ]`，实测后一次置 `[x]`。形态裁剪不改变任何 gate A 层结构标记要求。

### 阶段 1：需求与规格定义（Doc-First）

- **产物**：`docs/<feature>/01-spec.md`（必须定义 `REQ-xxx`）
- **必含清单**：
   1. **需求梳理**：业务背景、问题描述、用户场景（用户故事）、现状与期望差距。
   2. **功能需求清单**：每条含 `REQ-xxx` 编号、需求描述、优先级（P0/P1/P2）、**验收标准（DoD）**。
   3. **非功能需求**：性能指标、安全约束、兼容性（前后端/多租户/接口向后兼容）、可用性。
   4. **边界与约束**：明确**不做**的事（Out of Scope）、依赖项、外部系统契约。
   5. **输入输出契约**：字段级定义（字段名/类型/是否必填/取值范围/示例），便于设计阶段直接转接口规格。
   6. **需求来源与评审**：需求来源（用户反馈 / 缺陷 / 评审结论 / 业务决策）、需求评审结论（可测性、优先级对齐、是否进入开发）。

- **需求变更管理（追加式）**：开发中需求变化时更新 `01-spec.md` 采用**追加式**——新增 `REQ-xxx` 或经 CHG 记录，**保留历史需求/决策原文，禁止覆盖旧记录**（与门禁 3 测试报告批次保留同精神）。**总册联动（v3.35.0）**：REQ 新增/变更/裁剪同步回填 P01 总需求册（全景索引 + 业务流程总图受影响处），留变更注记（§1.3）。
- **验收标准**：A 层——每条 REQ 含 `REQ-xxx` 编号与验收标准（DoD）字段（命令见速查表「阶段 1」行，有输出）；B 层——需求 Agent/业务 Owner 确认每条 REQ 可测试、可追溯到 TC，无"模糊需求"（禁止"优化体验"类不可验证描述），留 Agent 标识（§2.1.7）；命中合规敏感域或 L2+ 时行业专家独立签署（§2.2）。

### 阶段 2：业务与技术影响分析（先分析、后方案）

- **产物**：`docs/<feature>/02-code-impact-analysis.md`
- **必含清单（三维影响，缺一不可，v2.20.0）**：
   1. **业务影响**：受影响业务流程与用户场景（端到端旅程）、上下游系统与数据流、行业/合规约束（如金融、医疗、数据出境）、SLA 与体验阈值——从行业与业务视角回答"这个变更会改变什么业务行为、波及哪些流程"。
   2. **技术影响**：调用拓扑图（入口→链路→出口）、受影响类/文件清单、爆炸半径（Blast Radius）评估（含被波及的"看似无关"调用方与共享组件）；命中状态/触发链路类变更时，补做隐式链路三向遍历（正向调用点 / 反向 watcher·事件·钩子 / 事件源×归宿矩阵），方法见 `docs/methodologies/state-trigger-audit.md`（v3.4.0）。
   3. **风险与回滚**：风险矩阵（概率 × 影响表，高风险项附缓解措施）、回滚策略。
- **先分析后方案（强制顺序）**：本阶段未完成前禁止进入阶段 3 方案设计；方案未覆盖本阶段识别的影响面即打回（§5）。
- **验收标准**：A 层——02 含「业务影响」节与「风险」「回滚策略」关键词及隐式链路遍历记录（命令见速查表「阶段 2」行，四条全通过；「隐式链路三向遍历」节标题或"隐式链路三向遍历：未命中"声明行均含此关键词，防止无关"未命中"字样绕过校验）；B 层——架构-计划 Agent 双视角核对：影响清单覆盖全部受影响流程与上下游、拓扑与代码一致（时点快照未改写）、抽查隐式链路入表，留标识（§2.1.7）；行业/合规约束由行业专家复核（§2.2）。

### 阶段 3：方案设计与任务拆解（Design）

- **产物**：`docs/<feature>/03-modification-plan.md`（定义 `DES-xxx`）+ `docs/<feature>/03.5-tasks.md`
- **必含清单**（按功能规模取用，新增功能全项必含）：
   1. **架构设计**：分层/模块归属、依赖方向、新增组件说明。
   2. **接口/API 设计**：HTTP 方法、路径、**请求/响应字段表**（字段/类型/必填/说明/示例）、状态码与**错误码**定义、示例报文。
   3. **流程设计**：时序图/流程图（mermaid 或 UML），标注正常流、分支流、异常流、降级流。
   4. **数据设计**：表结构变更、索引、缓存策略（key/过期/容量）、事务边界。
   5. **技术选型与决策记录（多方案强制对比，v2.20.0）**：**≥2 候选**对比矩阵（复杂度/性能/可维护性/熟悉度/成熟度与前沿性/风险与回退成本），结论论证「为何最适配当前业务」（规模、团队、演进路径）；前沿技术标注试验风险与回退路径；背景入 ADR。**M0–M3 分级与适用对照以 `docs/METHODOLOGY.md` 为唯一权威**——越级选型按其 §4 判过度设计。**禁止无对比定方案**（§5）。
   6. **兼容性与影响**：对既有调用方（Controller/WS/前端）的兼容措施；破坏性变更的弃用策略见 §2.13.3。
   7. **任务拆解（PM 标准，v2.20.0）**：WBS 原子任务（可独立提交/回滚），标注**依赖与关键路径、并行组、粗估、里程碑、DoT（可验证退出条件）**，关键路径留风险缓冲；**每个 CHG 必须在 `03.5-tasks.md` 追加任务行（T-next）或显式标注"CHG 直接实施（未拆任务，理由）"**，禁止无任务归属（防断环）。
   8. **总册联动（v3.35.0，§1.3）**：按 `docs/methodologies/project-masters.md` §2「回填触发面」逐册判定并回填（方案类通常触及 P02/P03/P04/P05/P11），未触及册在 09 回填清单标"未命中（理由）"；实文回填处留变更注记。

- **验收标准**：A 层——03 含 DES 编号与「备选/选型」对比内容，03.5 含 T 任务行（含依赖/里程碑标注）或 CHG 豁免标注（命令见速查表「阶段 3」行）；B 层——计划角色以**架构师 + 项目经理双视角**确认：每个 `DES-xxx` 可向下映射到代码（CHG）与测试（TC）、技术选型有 ≥2 候选对比且业务适配论证成立、任务拆分含关键路径与里程碑、接口变更给出前后兼容说明，留 Agent 标识（§2.1.7）；项目管理专家执行漏项检测（§2.2）。

### 阶段 4：测试脚本先行（Test-First）

- **产物**：`docs/<feature>/04-test-scripts.md`（定义 `TC-xxx`）
- **必含清单**：测试命令（JDK/Maven 全量命令）、用例矩阵（TC 编号/场景/输入/期望断言/**覆盖维度**/覆盖的 REQ-DES）、**业务场景清单（SC-xxx 五维全景枚举，见下）**、TDD 红→绿运行方式；测试 Agent 的独立性声明（§2.1）。**总册联动（v3.35.0）**：TC/SC 增删与测试策略变化回填 P06，批次结论与覆盖率回填 P07（§1.3）；**bug 修复落点不被既有 TC 覆盖时必须新增防回归 TC**（§2.5 阶段 6 条款 ②）。
- **变更动态约束**（如适用，v3.10.0）：从本变更 spec 与**前序产物**合成的不变量——类型参考 SCHEMA/协议/关系型/溯源型/时序型/能力型（arXiv:2602.02475 附录 F）；每条含检查方式与**显式失败路径**；step-by-step 合成优于 one-shot（§4.4 实证）。
- **覆盖维度矩阵（v2.20.0；v3.2.0 扩为十一类）**：功能正常流 / **业务场景**（端到端旅程，按 01-spec 用户故事）/ **逻辑分支** / 边界值与空值 / **异常与降级兜底**（依赖故障注入：超时/限流/5xx，覆盖 LLM 与非 LLM；重放与幂等）/ **数据组合与状态** / **并发与竞态**（引入共享可变状态/锁/线程池/异步时**必须**，联动 `methodologies/development.md` §3.6；未引入方可标"不适用"）/ **安全**（越权/注入/敏感数据，如适用）/ **兼容性**（接口前后兼容、多端）/ **性能与容量**（命中 01-spec 非功能指标时**必须**；未命中显式标注）/ **回归**（受影响既有功能）。L0/L1 可裁剪但**逐维显式标注"不适用，理由"**，禁止静默裁剪（§2.16.6 第 3 条）；**风险联动（v3.2.0）**：L3 安全维度强制（命中 PII/认证授权/对外接口不得标"不适用"）、命中性能指标时性能维度强制；变更按门禁 2 判定**复用 vs 新增**（打点必须断言内容，合入前跑全量回归）。

- **业务场景全景枚举与覆盖率（v3.3.0，业务专家视角）**：从用户故事按**五维**枚举——①角色/权限 ②状态与迁移 ③端到端链路（含跨模块）④时序与并发 ⑤异常业务路径——**隐含场景必须入清单**。落 04「业务场景清单」节（SC-xxx + 描述 + 关联 REQ + 覆盖 TC，追加式，每条 SC 至少映射一个 TC）；**覆盖率 = 已覆盖/枚举 ≥80%**（L3 ≥90%，未覆盖登记 FU-xxx）并逐条标注理由，禁止静默裁剪（§2.16.6 第 3 条）；`begin` 校验 SC- 编号；L0 纯文档变更可单条 SC 标"无业务场景影响"——禁止留空。
- **验收标准**：A 层——04 含 TC 编号、用例矩阵含「覆盖维度」列、业务场景清单含 SC 编号（命令见速查表「阶段 4」行）；B 层——测试 Agent 以**测试专家 + 业务专家双视角**核对：十一类覆盖维度均有用例或显式"不适用"标注（无未声明缺口）、业务场景五维枚举完整（含隐含场景）且每条 SC 有 TC 映射、场景覆盖率达标（≥80%，L3 ≥90%，未覆盖项有理由与 FU 登记）、正常/边界/异常全覆盖（门禁 2）且复用 vs 新增判定留痕，独立性声明附 Agent 标识（§2.1）；**NFR 反向核对**：`01` 声明的每条非功能指标（性能/容量、并发、安全、兼容、可靠性、可观测）须有 TC 映射或显式"未声明"判定，缺映射即退回（§2.2）。

### 阶段 5：代码实现（Coding）

- **产物**：源码（在关键改动处标注 `CHG-xxx`）+ 对应测试类 `*Test.java` + **编码记录 `04.5-coding-record.md`（v3.7.0，gate stop/CI 校验存在且非空）**——必含：改动文件清单（文件 / TASK / 改动类型 / CHG-xxx 标注落点 / 说明）、WHY 决策记录、ReAct 编码段（可指向 09）、新增依赖与理由。
- **中文注释规格（强制）**：① 类/接口：`@author` + 职责一句话；② 方法：公共 API/复杂逻辑/契约变化说明职责、`@param`/`@return`/`@throws` 与业务约束（简单私有方法不强制 Javadoc），改动处最小范围标 `CHG-xxx`；③ 关键逻辑 **WHY 注释**：解释"为什么"（业务原因/边界取舍/防坑），非 WHAT；④ 契约字段：DTO/VO 新字段注释含义与可空性；⑤ 降级/兜底路径：异常分支注明触发条件与降级行为。


- **编码约定**：沿用既有代码风格；防御性编程（判空/异常不吞掉）；敏感信息不入日志；新增依赖需说明理由并做供应链审核（§2.13.2）。工程决策细则见 `docs/methodologies/development.md`（M0/M1 基线）；数据结构建模见 `docs/methodologies/data-structures.md`（M0 基线，含弱类型穿层禁令）。
- **ReAct 微循环（v2.21.0，每次源码修改强制）**：每次改动前 **Thought**——分析当前状态、修改目标与影响面（引用 02 三维影响分析，含被波及的调用方与共享组件，§2.16.2 铁律）；改动后 **Observation**——运行受影响测试与验证命令并记录关键输出。**禁止"上来就改代码"**（§5 严重违规）。
- **验收标准**：A 层——关键改动处含 `CHG-xxx` 标注，且 `04.5-coding-record.md` 存在且非空并携带溯源块、变更目录全部 `*.md` 均携带溯源块（v3.17.0 单件 → v3.26.0 全产物，禁手写；命令见速查表「阶段 5」行；gate stop/CI 机器校验）；B 层——Review Agent 审查："无 WHY 注释"或"注释只复述代码"一律打回（见 §5 Anti-Patterns），留 Agent 标识（§2.1.7）；安全/性能专家增量评审（命中威胁面/性能红线时，§2.2）。

## 2.6 部署、配置与数据库变更规范（Deployment / Config / DB Change Standard）

> **触发条件（任一命中即必须遵守本节）**：改动了配置文件、新增了配置项、调整了中间件/缓存/依赖，或存在任何数据库变更。**禁止"代码改了、配置靠口口相传"、禁止"直接手改生产库"。**

### 2.6.1 适用范围（Scope）

凡涉及以下任一项的变更，除走 REQ → DES → CHG → TC 常规流程外，**必须**额外维护独立部署配置文件 `docs/<feature>/06.5-deployment-config.md`：

| 类别 | 典型对象 | 例子 |
|---|---|---|
| **项目配置** | `application*.yml`/`bootstrap.*`/`*.properties`/`pom.xml`/`logback-*.xml` | observability 开关、新增依赖、日志级别 |
| **Nacos / 注册中心** | dataId / group / 命名空间 / 灰度发布 / 动态刷新 | 新增 dataId、修改 group、配置灰度 |
| **Redis** | key 设计、过期时间、容量、序列化方式、连接池、分布式锁 | 新增缓存 key、TTL 调整 |
| **本地缓存** | Caffeine 等内存缓存 | maximumSize / expireAfterAccess 调整 |
| **中间件/其他** | MQ、线程池、Druid、第三方 SDK | 线程池容量、慢 SQL 阈值、SDK 版本 |
| **数据库变更** | DDL / DML / 索引 / 存储过程 / 数据订正 | 建表、加列、加索引、INSERT 数据脚本 |

### 2.6.2 必含产物：`06.5-deployment-config.md`

每个命中 §2.6.1 的变更，必须在该文档中追加记录。**必含清单**：

1. **配置变更记录表**：配置项全名（key）/ 变更前值 / 变更后值 / 生效范围（环境、租户、生效方式：重启 or 热更新）/ 变更原因（关联 `REQ`/`DES`/`CHG`）。
2. **数据库变更脚本规范**：
   - 脚本编号 `DB-xxx`，文件名约定 `V{序号}__{描述}.sql`（如 `V1__add_feature_config.sql`）。
   - 优先提供迁移脚本与回滚/前向修复脚本。若 DDL、数据订正或已对外暴露的数据无法安全无损回滚，必须明确标注**不可逆**，给出备份/校验、灰度或停机窗口、前向修复方案，并由 Release Owner 批准。
   - 脚本必须可重复部署：使用版本化迁移工具时依赖其版本记录保证一次性执行；仅对语义安全的对象使用 `IF NOT EXISTS` / `ON DUPLICATE KEY` / 先查后插。禁止用幂等语句掩盖环境漂移，执行前后须校验 schema/数据状态。
   - 禁止手改生产库；任何数据变更必须走版本化脚本并记录执行人 / 时间 / 环境。

3. **矩阵关联（第五维度映射）**：每条配置/DB 变更必须映射到 REQ / DES / CHG / TC（见 2.6.3）。
4. **验证方式**：该配置/DB 变更的验证命令或 SQL 校验语句（如 `mvn test`、`SHOW INDEX`、`SELECT count(*)`），结果入 `05-test-results.md`。
5. **敏感信息红线**：密码 / token / AK-SK 等**严禁**写入 git 与日志明文；走 Nacos 加密 / 环境变量 / 密钥管理（如 1Password）；日志脱敏。

### 2.6.3 配置/DB 变更追踪矩阵（CFG/DB 映射模板）

RTVM（§1.2）在此场景**扩展第五维度**。以下映射表与 RTVM 并列维护：

```markdown

| CFG/DB 编号 | 变更项（key/脚本） | 范围/环境 | 关联需求 | 关联设计 | 关联变更 | 关联测试 | 验证状态 |
|---|---|---|---|---|---|---|---|
| `CFG-001` | `feature.observability.enabled=true`（application.yml） | dev/test | `REQ-003` | `DES-003` | `CHG-002` | `TC-003` | ✅ PASS |
| `DB-001` | `V1__add_feature_config.sql` | 全部环境 | `REQ-003` | `DES-003` | `CHG-002` | `TC-004` | ✅ PASS |
```

### 2.6.4 记录更新要求（Changelog 联动）

- 09「方案」节必须列全部配置/DB 变更清单（CFG/DB 编号 / 变更项 / 目的）并链接 06.5。
- 「未动项」节声明未变更的关联配置/库表（如"未调整 Druid 慢 SQL 阈值"），防重复排查。
- 配置/DB 变更无 changelog 记录 = **未闭环**（§5）。

## 2.7 发布与上线流程规范（Release & Deploy Standard）

> **触发条件**：任何 CHG 合入主分支后进入发布，或涉及生产环境变更（代码 / 配置 / DB / 模型）。规范只到"提交"是不够的——上线后才发现的问题成本最高。

### 2.7.1 环境顺序与发布检查单

- 强制环境顺序：`dev → test → staging（如有）→ prod`，禁止跨环境跳过（热修复例外见 §2.11）。
- **发布检查单（全部通过才可发布）**：
   1. 合入条件齐备：09 §4 必填字段完整，RTVM/CFG-DB 矩阵闭环（门禁 4），独立测试、Review 与必要授权（门禁 5）。
   2. 全套件测试通过，证据在 changelog（门禁 3）。
   3. 配置/DB 已记 `06.5-deployment-config.md` 且**目标环境已应用**（§2.6）。
   4. AI/LLM：模型/endpoint 目标环境可用性验证通过（§2.9.1）。
   5. 监控/告警已配置且**冒烟观测有数据**（§2.8）。
   6. 回滚预案就绪：代码 tag、配置旧值、DB 回滚脚本（§2.6.2）。


- 发布动作本身记录到 changelog「发布与回滚记录」字段（§4 第 8 要素）。

### 2.7.2 上线冒烟验证（Post-Deploy Smoke Test）

- 发布后必须对**受影响链路**执行冒烟：主流程至少调用一次，验证返回正确 + 日志/观测有数据。
- 冒烟命令/步骤与结果写入 `05-test-results.md` 的发布节。
- **冒烟失败 → 立即进入回滚（2.7.3）**，禁止带病观察。

### 2.7.3 回滚标准与决策

- 触发回滚判定：P0 功能不可用、数据错误、性能劣化超基线、安全事件。
- 决策人：Release Owner；紧急情况下由当班负责人先处置，并在事后补齐 Release Owner/技术负责人确认。开发 Agent 或当次 CHG 执行人可提出建议，但无权单独接受生产风险。
- 回滚内容：代码回退 tag + 配置恢复旧值 + DB 回滚脚本（成对，§2.6.2）。
- **观察窗口**：发布后 24h 观察期，重点监控告警、错误率、慢查询；观察期结论记录回 changelog。

## 2.8 监控、告警与可观测门禁（Monitoring / Alerting Gate）

- **触发条件**：新增/修改任何用户可见链路、异步任务、外部依赖调用。
- **强制动作**：
   1. 链路接入可观测（结构化日志/logger/trace）并**验证观测确有数据**——防"观测 0 字节"（典型教训：HTTP 链路未接 tracer，日志为空无人发现）。
   2. 定义关键指标与告警：错误率、P95、慢 SQL、外部依赖（LLM）失败率。
   3. **未定义告警的 P0 链路禁止上线**；阈值与接收人写入发布检查单。

- **产物**：告警配置清单（告警项 / 指标 / 阈值 / 接收人）记入 `06.5-deployment-config.md` 或 changelog 发布节。

## 2.9 AI/LLM 专项规范（AI / LLM Standard）

> 涉及 AI/LLM 调用的链路属于高风险变更面。除通用门禁外，必须遵守：LLM 输入输出与数据结构建模细则见 `docs/methodologies/data-structures.md` §4（M0 基线）。

### 2.9.1 模型与端点可用性（防 endpoint 404）

- 任何调用外部模型服务（如 OpenAI、Ark、Bedrock 等）的链路，上线前必须验证：模型 endpoint 存在、key 有权限、额度充足。
- 模型 ID / endpoint 属于**配置变更**：改模型必须走 §2.6（06.5 记录 + CFG 矩阵），并提供**目标环境**验证证据。
- 典型教训：生产配置的模型 endpoint 在当前账号下 404，测试环境临时换模型验证通过——**上线前必须在目标环境实测，禁止只靠本地/其他账号验证**。

### 2.9.2 提示词（Prompt）变更门禁

- prompt 视为代码：改 prompt = 改逻辑。必须：① 走库（禁代码写死）；② 升版本（INSERT 新行 status=1 + 旧行 status=0）；③ changelog 记录（含 CFG/DB 矩阵）。变更须附影响面说明与验证（TC 或人工核验样例）；**prompt/模型/采样参数变更必须维护版本化评估集（v3.2.0）**：固定输入集 + 结构断言 + 抽样人工评分，评估集登记 06.5（CFG 类），变更全量重跑记 05。


### 2.9.3 AI 安全与幻觉防护

- 信息不足**引导补充而非臆测**（提示词内建该原则）；输出按产品要求含免责提示。
- AI 输出不得作为唯一决策依据：关键结论保留人工确认路径。
- 降级路径（模型不可用/prompt 缺失/解析失败/空响应）必须定义并验证（门禁 2 异常流）。

### 2.9.4 敏感数据隐私与脱敏（PII）

- 用户输入 / 会话文本属**敏感隐私数据**：禁止未脱敏写入日志、明文入 git、输出到非授权终端。
- 发送外部 LLM 前确认授权边界与数据保留策略；日志落盘需脱敏（姓名 / 电话 / 住址 / 证件号 / 邮箱等 PII 字段）。
- 违反视为 🔴 严重违规（§5）。

### 2.9.5 成本控制

- 外部 LLM 调用关注 token 成本：新增/高频调用在 03-plan 说明量级预估；超长上下文用压缩策略（如上下文压缩组件、历史摘要截断等）。

### 2.9.6 会话与上下文纪律（Session Context Discipline，v3.24.0）

> 管会话形态的 token 成本（§2.9.5 管调用单价；量纲：cache_read = 上下文水位 × 轮数，单会话不换挡即成本乘数失控）。

- **单会话单主题**：只做一个变更/主题；禁止混排 bugfix 与 CHG 工作（串行拆会话）。
- **换挡阈值**：超过 50 轮、主题切换、或上下文长期高位（窗口逼近上限 / cache_read 异常）时，必须 handoff 后开新会话，从磁盘重建状态（§2.16.1）；每次交付前在 09「重要上下文」做**换挡检查登记**（当前轮数/是否换挡/理由）。换挡线未 handoff 时 `gate begin` 拒开新变更（v3.38.0，`AGENT_GUARD_ALLOW_OVER_WATER=1` 豁免并登记）；**会话红灯未清同样禁开新变更（v3.41.0）**——`.agent-state/session-gate-last.md` 含 `GATE RED` 且新于最后交付的 09-changelog 时 `begin` 拒绝（`AGENT_GUARD_ALLOW_OVER_RED=1` 豁免并登记 09「重要上下文」）。
- **水位与遥测机校（v3.38.0 引入，v3.39.0 通用化）**：`scripts/session-gate.sh count turn|count tool <name>` 是**harness 无关的计数通用层**（bash，零依赖）——Claude 适配器经 `UserPromptSubmit`/`PostToolUse` hook 转发、OpenCode 插件经 `chat.message`/`message.part.updated` 事件转发，其余 harness 接等价事件即可，无适配器零开销跳过。计数落盘 `.agent-state/session-tool-stats.json` 与 `.agent-state/session-water.json`；`agent-gate begin` 读磁盘水位超 `AGENT_GUARD_SESSION_TURN_LIMIT`（默认 50）即拒开新变更，豁免 `AGENT_GUARD_ALLOW_OVER_WATER=1` 须在 09「重要上下文」登记理由；无水位文件客户端检查跳过、防线后移，语义不变（§2.17.3.2）；超线时 `session-gate` 对超限每 10 轮注入 handoff 硬提醒（软执法，gate begin 为硬执法面）。阈值为拍定值，metrics 成本数据（§2.17.5）积累后复核硬化。
- **勘探预算机校（v3.39.0）**：`session-gate idle/status` 从遥测文件读工具调用数——单会话 `bash` >20 亮黄灯（软执法），要求合并检索/下放子代理并在 09「重要上下文」登记超标原因（量化基线见 AGENTS.md 纪律节；纪律 4 勘探下放自本版起为默认强制）。
- **过程违规**：明知超标续用同一会话按 §5 反模式登记，证据落 09「重要上下文」。
- **定向验证优先（v3.25.0）**：模块/单测级验证命令先行；全量回归仅由门禁（stop/staged/CI）统一触发，禁止随手裸跑全量（执行细则见 AGENTS.md 纪律节）。

## 2.10 测试数据与环境隔离（Test Data & Environment Isolation）

- **强制规则**：

- 已知教训：合法数据初始化脚本也必须登记 `DB-xxx` 并含清理/回滚说明（06.5 §2），禁止"静默写库"。

## 2.11 热修复快速通道（Emergency Hotfix）

- **适用**：生产 P0 事故（服务不可用 / 数据损坏 / 安全事件），走标准全流程会扩大影响面。
- **规则**：
   1. 门禁允许**并行**（先修 + 事后补文档），**不可豁免**：changelog 24h 内补齐、回滚预案、根因分析（§2.5 阶段 6）。
   2. 流程：确认事故 → 最小修复 → 冒烟（§2.7.2）→ 发布 → 24h 内补全 changelog / RTVM / 06.5 → 根因复盘。
   3. 每次热修复必须触发一次 §2.12 遗留项/复盘记录，防同类再发。

## 2.13 协作、依赖供应链与接口生命周期（Collaboration / Supply Chain / API Lifecycle）

### 2.13.1 分支与 PR 协作

- 分支命名：`{yyyyMMdd}-{feature|bugfix}-{简述}`（如 `260803-bugfix`）；禁止直接向主分支提交代码。
- 合入主分支必须经 code review（§2.5 阶段 8）并留 `07-review-report.md` 结论；重大变更需 ≥2 个审查视角（含 skill 交叉验证）。
- 开发、测试、Review 必须遵守 §2.1 独立性；PR/合入记录必须关联独立测试与独立 Review 的结论。高风险变更还须有 Release Owner 的明确授权。

### 2.13.2 依赖供应链

- 新增/升级依赖（pom 等）必须：说明理由（替代方案对比）、确认许可证与 CVE 风险（无扫描工具时人工检索）、**锁定版本**（禁止无版本号依赖）。
- 第三方 SDK（含 AI SDK）升级视为配置/依赖变更，记入 06.5。

### 2.13.3 接口生命周期与弃用策略

- 对外接口向后兼容：新字段只增不改语义；禁静默改类型/单位/默认值。
- 破坏性变更：过渡期（旧接口保留 ≥1 版本标 deprecated + 弃用日期）；版本化（`/api/v2`）可选。
- 弃用/移除在 changelog 显式记录，并在 `01-spec.md` 标注；**同步登记 P03 接口索引册**（接口总表状态列 + 破坏性变更时间线，§1.3）。

### 2.13.4 自动化质量门禁与例外

- CI/PR 必须自动执行并留存：编译、受影响模块测试、全量回归、覆盖率、静态分析、依赖/CVE 与许可证、密钥泄露扫描；适用时加接口契约、性能与迁移校验。自动化通过不替代门禁 5 独立判断。**跨文档一致性审计（v3.4.0）**：目标仓库可在 CI 加 `bash tests/audit-docs-consistency.sh`（G1 版本链 / G2 编号连续 / G3 §3↔§4 归档同源 / G4 bugfix 双登记互证 / G5 RTVM 回填一致 / G6 §4 必填节），失败项即存量回填清单（§2.14）——与 agent-gate 单产物 A 层校验互补（gate 管单件合格，审计管多件互证）。

- 所谓"全量回归"必须写明命令、范围、基线版本与结果；若因环境/时限不能运行，CHG 必须标记为**未完成/有条件通过**，列出风险、补偿措施、责任人和完成期限，禁止写成"测试通过"。
- **检查器设计规约（v3.10.0）**：新增任何门禁/审计检查必须两段式——①**结构 guard**（适用性判定：该步/该产物是否属于检查范围，不适用即 skip 不产生记录）；②**断言裁决**（guard 命中范围内判 sat/viol）；语义类检查三值化（**CLEAR_FAIL 才判罚，证据不足/歧义一律不判罚**）；检查代码必须含**显式失败路径**（防恒真）；上线前自查误报可能并修剪（过宽检查制造假通过信号——BUG-002 S1 教训）；根因判定须排除下游症状。依据：arXiv:2602.02475 §3.2/§4.7 与本项目 BUG-001/002。
- 任何门禁例外仅可由 Release Owner（高风险须技术/领域负责人共同）书面批准，记录适用范围、原因、风险、补偿措施、到期时间；例外到期自动失效，不能被 Agent 自行批准。

## 2.14 标准升级与存量文档回填（Governance）

## 2.16 变更执行主线与完成判定（AI 防漏）

### 2.16.1 执行前置（每个变更开始前，AI 必做）

1. 读 `AGENTS.md`（本规范强制入口）。
2. 核对**标准当前版本**（页脚 vX.Y.Z）与**标准升级日志**（`STANDARDS_CHANGELOG.md`，§2.14）——最近升级是否影响本功能文档（须回填的条款）。

### 2.16.6 防遗漏/防跳过强制执行规则（AI 专用红线）

> 约束 AI 最常见失效模式——**不是不知道规则，而是长任务中悄悄省略、用摘要代替核对、"大体完成"时提前标记**。本节优先级高于"效率/简洁"，不得以任务复杂为由减免。

1. **逐项引用核对（v3.23.0 起，替代旧"逐条抄录"）**：声称任一阶段/门禁/DoD 完成前，必须把对应清单（§2.16.3/§2.16.4/所属阶段 §2.5 必含清单）**逐项列出条目号并勾选** `[x]`/`[ ]`，每项附一句结论——A 层项附校验命令与**过滤后关键输出行**（勿贴全文），B 层项附独立角色签署；**不要求抄录清单原文**（条目号引用即可，原文只在规范一处留一份，上下文与产物双份 verbatim 复制是反模式），禁止总结句代替，无逐项清单佐证的完成声明无效。
2. **缺失即未完成**：任一项无对应产物/证据即该环节未完成，不得整体标记"完成"，必须继续执行或明确报告"未完成 + 阻塞原因 + 所需输入"；**不允许大部分已完成就整体标完成。**
3. **禁止静默降级/跳过**：不得以"看起来不重要"自行跳过；跳过必须写明编号与理由，并区分"未命中，不适用"（§2.5）与真跳过。
4. **禁止"部分执行当全部执行"**：例如全量回归只跑了受影响模块，不得在清单勾选"全量回归通过"，必须如实标注"部分回归"并按 §2.13.4 走"未完成/有条件通过"流程。
5. **预算不足显式声明**：预估步骤/token 不足以完成全部 10 阶段 + 5 门禁时，须不晚于阶段 3 向编排者/人类声明"建议分批，已完成到 ___ 阶段"，禁止结尾才发现遗漏或压缩执行深度（如把跑测试简化为"预期会通过"）。
6. **完成声明的最终格式**：AI 在一次变更的最终交付消息中，必须包含以下三部分，缺一不可：
   ① 本次风险等级判定（§0.5）及理由；
   ② §2.16.3 DoD 全部条目逐条 `[x]`/`[ ]` 结果（不可用"以上均已完成"代替逐条罗列）；
   ③ 如有任何 `[ ]` 未完成项，列出后续处理人与预计完成方式。
7. **复核义务**：编排者/人类采信子 Agent"已完成"结论前，必须按第 1 条抽查清单对应产物是否真实存在（如 05 是否真有本批次控制台输出），不得仅采信汇报；不符按 §5"口头宣称测试已通过"同级处理。

### 2.17 变更管线自动化扩展（传动机制、事故重入、自主权分级、自测试）

> 本节把 §2.16 执行主线从"人/AI 逐阶段驱动"扩展为"产物驱动"：产物合入即确定性触发下一阶段的骨架派发（传动机制）；生产事故作为新的意图重入管线（§2.5 阶段 6 的自动化入口）；一切自动化动作按环境分级授权；治理配置自身必须通过 golden-case 回归测试。**铁律：自动化只生成骨架与登记，不生成产物正文**（防臆造，同 §2.16.6 精神；违者触发 §5）。

> **外部研究依据（v2.18.0）**：「状态外置、只信磁盘」的实证——CIKM '26《The Compaction Cliff》（[arXiv:2608.22752](https://arxiv.org/abs/2608.22752)）：/compact 一轮后安全规则仅存 53%、五轮后 10%，去验证器的系统「报告 100% 保留、实际静默丢失 57% 约束」；流程侧（意图漂移、决策不可复盘、事故不回流）见 Anthropic《[The AI-Native SDLC Playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)》。故铁律：治理状态外置磁盘产物；写盘后以 shell 级验证（`grep -c`/`wc -l`/`git diff`）确认落盘，不采信工具返回值或 Read 缓存；门禁只读磁盘与 git。

> **管线入口产物 `00-intent.md`**：每个变更在进入阶段 1 之前必须先落 `00-intent.md`（问题 / 预期结果 / 受影响用户与系统 / 约束 / 开放问题 / 意图澄清记录，模板见 skill 资源 `intent.md`）。阶段 1（门禁 1）将其转写为 `01-spec.md` 的 `REQ-xxx`；无 `00-intent.md` 的变更视为无意图变更，可执行门禁（`agent-gate begin`）拒绝放行。`00-intent.md` 为追加式文档（§2.15），可由需求角色、人类或监控系统创建；开放问题未全部关闭前不得进入阶段 3。

> **管线治理声明 `00-governance.json`**：与 `00-intent.md` 同目录创建，声明本次变更治理元数据——`change_id`（与变更目录名一致）、`risk_level`（L0-L3，§0.5.1）、`implementation_owner` / `test_owner` / `review_owner`（执行主体标识，§2.1.7 格式）；**L2/L3 变更 `test_owner` 与 `review_owner` 必须与 `implementation_owner` 互异**（§0.5.2/门禁 5），否则 `agent-gate begin` 拒绝放行。执行主体标识不得为占位符（`PENDING`/`TODO`/`TBD`/`待定`；`implementation_owner` 恒检，`test_owner`/`review_owner` 按 L2/L3 检查，v3.5.0）；**L3 变更另须含释放授权三字段** `release_authorized_by` / `release_authorized_at` / `release_authorization_evidence`（全部非空，缺失即 `agent-gate begin` 拒绝放行）。**缺陷修复变更须声明 `bug_ref`**（v3.6.0，可选字段，值为本次处置的缺陷编号如 `BUG-042`）——非空时 `agent-gate begin` 校验 `docs/bugs/<bug_ref>/` 下缺陷文档组六件（`01-diagnosis.md`/`02-impact.md`/`03-test-plan.md`/`04-matrix.md`/`05-config.md`/`06-tasks.md`；v3.6.0 三件、v3.7.0 扩六件）存在且非空（根目录 `AGENT_GUARD_BUGS_ROOT` 可覆盖，默认 `docs/bugs`），缺失即拒绝放行；非缺陷修复留空字符串跳过校验。创建后不可变（§2.15）；风险等级修订（§0.5 降级判定禁令）记录到 09 CHG「重要上下文」，不改写本文件。模板见 skill 资源 `governance-state.json`。

> **产物目录双轨约定**：变更管线产物（`00-intent.md`/`00-governance.json` 及 `agent-gate begin` 必检 7 件）落**变更目录** `docs/changes/<变更号>/`（默认根；`AGENT_GUARD_CHANGE_ROOT` 可覆盖），gate 以该目录为核对根；`docs/<feature>/` 为功能级长期文档（05/06/07/09、01.5 矩阵、06.5 等）的权威落点（§2.5）。变更目录中的 01-spec/02/03/03.5/04 为门禁入口件，与功能目录同名文档须为同一内容（同文件或同步回填），禁止两处分叉；05/09 因 gate stop 在变更目录核证（05/09 存在性），同样双落点同步；§2.5 各阶段校验命令中的 `docs/<feature>/` 路径在管线启用时按变更目录对应解释。**`01.5-rtvm-matrix.md` 属审计层边界（v3.7.0）**：该矩阵**单落点、不两处分叉**（§1.2）——有功能目录的仓库落 `docs/<feature>/`，**无功能目录的仓库（本规范源仓即此类）落 `<变更根>/<变更号>/`**。其回填**内容**正确性由通用层审计 G5（门禁 4 机器兜底，§2.13.4）与 B 层 Review 承担；`agent-gate` 的 `validate_delivery` **不把它当作本变更的必检产物**（不校验存在与节完整性），但**读取 `docs/*/01.5-rtvm-matrix.md` 与 `<变更根>/*/01.5-rtvm-matrix.md`（深度 1）做「门禁 4」回填核对**——`09-changelog.md` 引用的每个 `REQ-` 须在其中一份成行。——八类映射中「矩阵」类的 gate 侧校验以 01.5 双落点协议与审计/Review 为准，非静默缺口。**治理工具自身**（scripts/agent-gate、scripts/install-hook-adapter、scripts/check-standards-compliance.sh、tests/run-tests.sh、tests/audit-docs-consistency.sh、.githooks/、hook 适配器配置）不视为产品代码——安装/升级它们的提交不需要变更产物，由 §2.17.4 golden-case 回归背书。

> **本地 Git Hook 强制面（v3.5.0）**：`commit-msg` 归因闸门（`agent-gate --stage commit-msg <msgfile>`，模板 `resources/templates/commit-msg`）——暂存区含代码文件的提交消息必须引用有效变更号，豁免阶梯：合并提交（MERGE_HEAD 存在）、以 `Revert` 开头、纯文档/纯产物提交（无代码文件）；branch 模式（`--stage ci --base <ref>`）对 diff 触及的变更追加 delivery 证据核验（05+09 与 Observation，§2.17.5）；`pre-push` 模板接线 `--stage ci`（base 取 upstream，无 upstream 退化为 HEAD）。**安装器自动接线（v3.11.0）**：`bootstrap --guard` 自动配置 `core.hooksPath`（已有自定义值不覆盖）、自动生成客户端适配器（检测到客户端时）、自动探测构建系统测试命令预填 `.agent-governance.yml`；gate 验证命令来源链 = `AGENT_GUARD_VERIFY_COMMAND` env → yml `ci.verification_command`（占位符跳过）→ 未配置跳过。

#### 2.17.1 传动机制（Artifact Pipeline）

0. **入口件脚手架（v3.38.0）**：`scripts/new-change <变更号> --risk Lx`（随 `--guard` 安装）从 `<docs>/templates/entry/` 生成 begin 必检七件骨架，自动判定专用目录 / 当日批次归并（L0/L1 默认入批、L2/L3 一律专用、`AGENT_GUARD_ALLOW_INDEPENDENT=1` 豁免同 gate 语义）；骨架只含章节标题与待填注释，治理 JSON 执行主体占位 `PENDING` 由 begin 占位符校验拒绝——**脚手架不消除任何门禁，只消除"入口三件无模板"的空白**（此前 §2.17 派发仅覆盖 01 合入之后的 02/03/03.5/04，入口件无一致起点）。
1. **触发规则**（确定性、基于产物路径，不依赖自然语言判断）：
   - `01-spec.md` 合入主干 -> 自动创建 `automation/<变更ID>-scaffold` 分支，按阶段顺序派发 `02-code-impact-analysis.md`、`03-modification-plan.md`、`03.5-tasks.md` 与 `04-test-scripts.md` 骨架并开 PR（骨架集必须覆盖 `agent-gate begin` 必检七件之差集——01/00-governance 已在管线入口落盘，否则 begin 必失败；v3.4.0 补 03.5）；
   - `09-changelog.md` 合入主干 -> 自动开发布检查单 issue（§2.7.1 六项：回滚预案、配置核对、DB 脚本核对、监控告警、灰度计划、发布授权）。
2. **骨架约束**：骨架只含章节标题与待填注释，禁止预生成方案/测试内容（防臆造）；正文填写仍由方案/测试角色经门禁 1/2 完成，自动派发不豁免任何门禁。
3. **频控**：目标分支已存在即跳过，防止重复触发。
4. **平台无关性**：参考实现为 GitHub Actions（skill 资源 `github-artifact-pipeline.yml`）；GitLab 等平台用等价 CI 触发规则 + 平台 API 实现同一语义，**语义以本节为准而非以具体平台为准**。

#### 2.17.2 事故重入管线（Incident -> Intent）

1. **闭环语义**：事故 = 未被记录的意图。任何生产事故（告警、故障、SLO 违约）必须转化为一个新变更的 `00-intent.md` 骨架（编号 `BUG-<UTC 时间戳>`），禁止"修完不留痕"；事故处置随后走 §2.5 阶段 6 诊断，生产事故同时遵守 §2.11 热修通道。
2. **触发方式**：监控/告警系统调用代码托管平台的事件接口（如 GitHub `repository_dispatch`，类型 `incident`）并附带告警元数据（source / metric / current / threshold / severity / triggered_at / detail_link）；参考实现见 skill 资源 `github-incident-to-intent.yml`。
3. **频控与注入**：目标分支已存在即跳过（防告警风暴）；元数据以「自动注入，勿删」节写入骨架，接手者按 §2.16 主线补全。
4. **自主权上限**：本管线只创建文档骨架与 PR（A2 级，见 §2.17.3），不自动修复、不自动合入、不触碰生产环境。

#### 2.17.3 分环境自主权分级（自动化动作授权矩阵）

| 级别 | 动作类别 | 示例 | 授权环境 |
|---|---|---|---|
| A0 | 只读观察 | 查询 diff、输出度量（§2.17.5） | 任意环境 |
| A1 | 登记 | 创建 issue / 评论 / 打标签 | 任意环境 |
| A2 | 骨架 | 创建分支 + 骨架文件 + PR | 任意环境（合入仍需人类/角色审查） |
| A3 | 内容 | 填充产物正文、修改代码 | 仅本地/沙箱；门禁照常生效 |
| A4 | 执行 | 跑测试、合并、部署 | 跑测试限本地/沙箱；合并/部署永远需门禁 5 与人类授权 |

1. 本规范配套的全部托管平台 workflow 自主权上限为 **A2**；A3/A4 由 Agent 在本地开发环境执行，合入门禁（§2.16.3 DoD、门禁 5）不因自动化而豁免。
2. **客户端兼容第二维度**：支持 pre-write Hook 的客户端（Claude Code、Gemini CLI 等）三层全开（Hook 建议 + 脚本强制 + CI 边界）；不支持 Hook 的客户端/IDE 退化为 Git Hook（staged/stop）+ CI 兜底，**语义不变、防线后移**，不得因客户端差异放弃任一门禁。

#### 2.17.4 治理配置自测试（Golden Cases）

1. 门禁脚本（`agent-gate.sh`）与 hooks/CI 模板属"治理配置"，必须可回归：`tests/run-tests.sh` 在临时 Git 仓库构造合规/违规状态（begin 缺产物、L2 角色不独立、占位符与 L3 授权字段缺失、bug_ref 缺陷组缺失/为空/非法 id、pre-write fail-closed、staged/stop/ci 各门禁、commit-msg 归因与豁免阶梯、度量词边界匹配），断言退出码与输出。

2. 修改 `agent-gate.sh`、hooks 或 CI 模板的变更必须先跑通全部用例再合入；用例与实现同仓同版本。
3. 测试套件零依赖（bash 3.2+ 与 git），macOS/Linux、任意 IDE 终端均可运行，作为 §2.13.4 自动化门禁对治理配置自身的适用。

#### 2.17.5 管线度量（metrics）

1. `agent-gate metrics` 以 JSON Lines 输出每个变更的阶段时间戳与间隔：`intent_ts` / `spec_ts` / `plan_ts` / `first_code_commit_ts` / `test_evidence_ts` / `changelog_ts`，间隔 `intent_to_spec_s` / `spec_to_plan_s` / `plan_to_code_s` / `code_to_evidence_s` / `intent_to_changelog_s`，以及 `delivery_ready`（05+07+09 三件齐备才为 true）；`expert_sessions`（01/03 署名节唯一任务 ID 去重计数）与 `expert_sessions_over_guardrail`（L2/L3 >3 超标标记，v3.34.0——行首三段斜杠形态的观测可能计入 REQ/DES 类编号行，属观测偏差可接受）；**`artifact_files` / `artifact_bytes`（v3.38.0）**——变更目录内 `*.md` 件数与字节量（治理 JSON 刻意不计，同盖章豁免口径），用于"规范瘦身"决策数据化（§2.17 引言减法方向）；批次内各成员报同一目录级数值（共享文件），**跨成员不得求和**。
2. 度量为 A0 只读观察，纯 git 历史与磁盘推导、零第三方依赖；任一端点缺失输出 `null`，禁止推测补值。token 级成本（cache_read_per_turn / 工具调用数）为平台运行时数据，不进本契约；需要时由平台侧 adapter 另行导出（v3.38.0 裁定）。
3. 用途：识别管线瓶颈（如 `spec_to_plan_s` 过长 = 方案阶段积压）与交付就绪状态；**禁止用度量数值替代 DoD 判定（§2.16.3）**。

## 4. Changelog 格式规范（核心交付物）

`09-changelog.md` 记录每次具体变更，是跨会话、跨 Agent 的承上启下记忆载体。每个 CHG 必须包含本节的追踪映射、现象、分析、根因、方案、测试结论、角色签署、执行检查清单与未动项；命中 §2.6 时「方案」含配置/DB 清单，进入发布时另加「发布与回滚记录」字段。**每个 CHG 的「追踪矩阵映射」节为短引用**（需求/设计/测试编号 + 链接 `01.5-rtvm-matrix.md`），完整矩阵在独立文件 `docs/<feature>/01.5-rtvm-matrix.md`（§1.2）——两处必须同步回填：

```markdown

- 对应设计：`DES-xxx`（见 03-modification-plan.md）
- 对应测试：`TC-xxx`（见 04-test-scripts.md / *Test.java）
```

## 5. 常见违规行为与拦截策略（Anti-Patterns）

| 违规行为 | 严重等级 | 门禁拦截策略 |
|---|---|---|
| **跳过文档直接改代码** | 🔴 严重违规 | 触发【门禁 1】拦截，必须先回退代码，更新 `01-spec.md` 和 `03-modification-plan.md` 后重新开始。 |
| **改完代码不写/不跑测试** | 🔴 严重违规 | 触发【门禁 2 & 3】拦截，禁止宣称完工，必须补全 `TC-xxx` 并执行 `mvn test` 提供真实终端输出。 |
| **口头宣称“测试已通过”** | 🔴 严重违规 | 触发【门禁 3】拦截，无脱敏测试摘要、退出码和受控原始日志制品链接者一律判为未完成。 |
| **同一 Agent/开发者自测、自审、自批** | 🔴 严重违规 | 违反门禁 5：重新分派独立测试与 Review；高风险变更补人类 Release Owner 授权后方可合入。 |
| **敏感用户数据（PII）/ 密钥 / token 明文写入 Git 文档、日志或其他落盘** | 🔴 严重违规 | 违反门禁 3/§2.9/§2.9.4（同一根因，v3.8.0 合并）：立即删除并按泄露流程处置（排查历史提交）；文档仅留脱敏摘要与受控制品链接。 |
| **门禁例外无授权、无到期时间或被 Agent 自批** | 🔴 严重违规 | 违反 §2.13.4：例外无效，变更退回；由有授权人重新评估风险与补偿措施。 |
| **孤儿代码（无 REQ/TC 映射）** | 🟡 中度违规 | 触发【门禁 4】拦截，要求在 RTVM 矩阵中补充上游需求来源与下游测试用例。 |
| **只更新 changelog 追踪矩阵、不回填独立 RTVM 矩阵文件** | 🟡 中度违规 | 触发【门禁 4】拦截，要求回填 `docs/<feature>/01.5-rtvm-matrix.md`（§1.2），含验证状态、编号顺序核对与四维链路。 |
| **RTVM 四维链路断环（REQ→DES→TASK→TC 任一环缺失）** | 🔴 严重违规 | 需求必须有设计、设计必须落任务、任务必须产出测试；断环即回填补齐，禁止跳环。 |
| **改动调用点打点未断言（执行≠覆盖）** | 🟡 中度违规 | 违反门禁 2 断言完整性，要求补充断言（如可观测记录事件/里程碑/终止原因）。 |
| **只跑受影响用例、跳过全量回归** | 🟡 中度违规 | 违反门禁 2 全量回归强制，要求跑 `mvn -pl <module> -am test` 全套件再合入。 |
| **测试报告覆盖/改写历史批次结果** | 🔴 严重违规 | 违反门禁 3 批次保留：`05-test-results.md` 历史批次原文/状态不得覆盖，须追加独立小节（§N）；修订须加「修订说明」。 |
| **标准升级未回填存量文档** | 🟡 中度违规 | 违反 §2.14：标准新条款必须回填所有既有功能文档，未回填视为未落地。 |
| **CHG 未回写方案正文 / 未拆任务（无豁免标注）** | 🟡 中度违规 | 违反阶段 3/9：CHG 必须回写 `03-modification-plan.md` 正文并拆 T 任务（或显式豁免标注），禁止只登记。 |
| **变更执行检查清单无落点（只在会话/工作区勾选）** | 🟡 中度违规 | 违反 §3 落点规则：勾选清单必须随 CHG 归档 `09-changelog.md`「变更执行检查清单」字段。 |
| **覆盖丢历史（活文档/配置/批次无追溯 / 改写已闭合 CHG / 06.5 改旧 CFG 行）** | 🔴 严重违规 | 违反 §2.15：历史批次/旧 CFG 行只增不改；已闭合 CHG 与已登记 BUG 只读，勘误新开一组（§2.15 规则 4，v3.6.0）。 |

| **RTVM 编号跳号/重号/重排历史编号** | 🟡 中度违规 | 违反 §1.2 编号顺序规则，要求按连续递增修正，历史编号禁止重排。 |
| **阶段产物缺失或未达规格下限** | 🟡 中度违规 | 按 §2.5 必含清单逐项核对，缺失即打回补齐后再进入下一阶段。 |
| **未做背景调研/影响分析直接出方案改代码（片面改动）** | 🔴 严重违规 | 违反 §2.16.1 第 4 步与 §2.5 阶段 2「先分析后方案」：退回补齐业务/技术/风险三维影响分析与背景调研结论；技术选型无 ≥2 候选对比同理打回（阶段 3）。 |
| **未经 Thought 直接改代码/文档（"上来就改"）** | 🔴 严重违规 | 违反 §2.16.2 ReAct 铁律：退回补全局影响分析与 Thought 记录；已产生改动重新评估影响面后可保留；09 缺 Observation 的阶段视为未闭环。 |

| **测试覆盖维度静默裁剪** | 🟡 中度违规 | 违反 §2.5 阶段 4：未设计的覆盖维度必须逐维度显式标注「不适用，理由」，退回补标注或补用例。 |
| **04 无业务场景清单（缺 SC-xxx）/ 场景覆盖率 <80% 无未覆盖理由** | 🟡 中度违规 | 违反 §2.5 阶段 4（v3.3.0）：`agent-gate begin` 拒绝缺 SC 的 04；未覆盖场景须逐条标注理由，L3 覆盖率 ≥90% 且未覆盖项登记 FU-xxx，退回补齐。 |
| **SC 场景无 TC 映射（凑数枚举）** | 🟡 中度违规 | 违反 §2.5 阶段 4：每条 SC 必须至少映射一个 TC，无映射视为凑数，退回补用例或删除无效场景。 |
| **专家评审模板泛评无项目证据 / 开发主体代签** | 🟡 中度违规 | 违反 §2.2 上下文贴近契约与署名禁令；A 层署名机校 FU-039 已落地（v3.34.0）。 |
| **一人多角色：同一主体兼任作者/实现/测试/评审** | 🔴 严重违规 | 违反 §2.1 规则 10 与 §2.2 两批制（生产批≠评审批）；无豁免声明即打回重派。 |
| **只口头宣称"已验收 / 已按规范产出"而不逐项引用该阶段验收标准条目号** | 🔴 严重违规 | 违反 §2.5 总则：该阶段判定未完成，退回逐项引用条目号并勾选；A 层必须附校验命令与关键输出，B 层必须附独立角色签署（含 Agent 标识）。 |
| **A 层校验只口头宣称"通过"、不附命令与输出记录** | 🔴 严重违规 | 违反 §2.5 A 层：必须把校验命令与关键输出记入 09「变更执行检查清单」，无记录视为未验收（开发 Agent 不得自评 B 层）。 |
| **把 L3 级全套仪式套在 L0/L1 变更上、无谓放大执行成本** | 🟡 中度违规 | 违反 §0.5 轻量通道指引（v3.23.0）：L0/L1 应按 §1.1 轻量通道裁剪表达成本（单行"未命中"声明 + 批次目录）；退回按轻量形态重整产物，已产生的大段冗余内容不追溯删除。 |
