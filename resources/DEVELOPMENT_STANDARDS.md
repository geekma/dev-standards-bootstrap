# 全局软件开发与变更规范（Development & Skills Standards）

> **【强制执行】本文件是项目全局最高开发规范**，适用于所有 AI Agent（Antigravity、Gemini、Claude、Cursor、Windsurf、Qoder 等）以及人类开发者。  
> **核心原则：文档先行、测试先行、全链路追踪矩阵映射、多 Skill 交叉验证、角色独立验证、按风险分级执行、逐项核对不遗漏。严禁无文档改代码，严禁未跑测试宣称完工，严禁同一执行主体自测、自审、自批，严禁用摘要/口头总结代替逐项清单核对（§2.16.6）。**
> **文档结构说明**：判定类内容（DoD、AI 防漏自检、风险分级、Agent 独立性、阶段产物验收标准）在全文各**只有一处权威定义**（§0.5、§2.16.3、§2.16.4、§2.5 总则），其余出现处均为强制引用而非另行改写；如发现两处表述不一致，以被引用的权威章节为准。

## 0. 五大核心硬性约束与阻塞门禁（Hard Quality Gates）

任何变更任务若未通过以下 5 道门禁，**一律禁止合入主分支或标记为完成**：

```ini
       [ 门禁 1: 需求/设计先行 ]
       需求有变/新需求 ──► 必须先更新 01-spec & 03-plan ──► 严禁直接改代码
               │
               ▼
       [ 门禁 2: 测试脚本先行 ]
       编写/修改代码前 ──► 必须在 04-test-scripts 编写 TC ──► TDD 红绿循环
               │
               ▼
       [ 门禁 3: 运行测试与证据闭环 ]
       宣称完工前 ──────► 必须命令行跑测试并截取实际输出 ──► 严禁口头声明成功
               │
               ▼
       [ 门禁 4: 全链路追踪矩阵闭环 ]
       提交变更时 ──────► 必须在 09-changelog 闭环 RTVM ──► REQ ↔ DES ↔ CODE ↔ TC
               │
               ▼
       [ 门禁 5: 独立验证与合入授权 ]
       合入/发布前 ──────► 测试与审查由独立角色完成并留痕 ──► 禁止作者自证、自批
```

### 门禁 1：需求与设计先行门禁（Doc-First Gate）

- **约束规则**：只要涉及业务逻辑调整、接口字段增删、行为策略变更，**严禁直接修改代码**。
- **强制动作**：
   1. 必须先在 `docs/<feature>/01-spec.md` 更新需求规格，分配/更新需求编号（如 `REQ-101`）。
   2. 在 `docs/<feature>/03-modification-plan.md` 中更新技术方案与设计决策（如 `DES-101`）。
   3. 确认影响范围与向下兼容性后，方可启动代码编写。

### 门禁 2：测试用例先行门禁（Test-First Gate）

- **约束规则**：禁止“先写完代码，上线前补个测试”或“完全不写测试”。
- **强制动作**：
   1. 必须在 `docs/<feature>/04-test-scripts.md` 明确对应的测试用例编号（如 `TC-101`）。
   2. 测试用例必须覆盖：**正常流（Happy Path）+ 边界值/空值 + 异常兜底流**。
   3. 遵循 TDD 理念：先写出能复现问题或验证新特性的测试脚本（Red），再编写实现代码（Green）。

- **变更测试策略（复用 vs 新增判定）**：
   - **新增**功能/新分支/新字段/新调用点打点 → **必须新增 TC**（覆盖正常+边界+异常兜底，§2.5 阶段 4）。
   - **修改**既有逻辑（行为变化）→ 复用既有 TC 全量回归；对新增分支/边界须**扩展断言或新增用例**。
   - **纯重构**（行为不变）→ 复用既有 TC 全量回归，可不新增；若重构暴露新边界，补用例。
   - **删除**逻辑 → 删除对应 TC 须在 `09-changelog.md` 记录，禁止静默删。
   - **断言完整性**：修改的调用点打点（如可观测记录）必须**断言其内容**（执行≠覆盖），禁止只"跑到"不断言。
   - **全量回归强制**：任何代码变更合入前必须跑全量测试套件（如 `mvn -pl <module> -am test`），禁止只跑受影响用例（防副作用/回归盲区）。

### 门禁 3：完工证据验证门禁（Evidence-Before-Assertions Gate）

- **约束规则**：严禁在未实际执行测试并取得控制台输出的情况下宣称“已修复”、“已完成”或“测试通过”。
- **强制动作**：
   1. 必须在终端真实执行测试命令（如 `mvn test ...`）。
   2. 在 `05-test-results.md` 记录**脱敏后的**命令、耗时、退出码、Tests run / Failures / Errors 与原始日志制品链接；原始日志只可存放在受访问控制的制品库，禁止将敏感用户数据、密钥或 token 复制进 Git 文档。
   3. 若因外部环境受阻无法自动化运行，必须提供可执行的手动验证复现命令或接口测试用例。
   4. **测试报告批次保留（禁止覆盖历史批次）**：每次变更在 `05-test-results.md` **追加独立批次小节**（如 `## 第 N 批 / §N：CHG-XXX ...`），**保留既有批次结果原文与状态**（历史 PASS/FAIL 不改写）；全量重跑时须同时给出"本次全量总数 + 与上一批对比（前 → 后）"；增量补强（如补断言/补用例）在当批或新批次小节记录，**不并入旧批次**；确需修订历史错误时加「修订说明」标注，禁止静默覆盖。

### 门禁 4：四维全链路追踪矩阵闭环门禁（Traceability Gate）

- **约束规则**：每一处代码改动都必须能向上追溯到需求，向下映射到测试；禁止无需求的“游离代码”，禁止无测试的“盲区代码”。
- **强制动作**：每次变更必须在 Changelog 中维护 **RTVM 追踪矩阵映射**（§4，短引用），并**回填所属功能的独立 RTVM 矩阵文件 `docs/<feature>/01.5-rtvm-matrix.md`**（§1.2：REQ→DES→TASK→TC 四维链路 + 验证状态）；只更新 changelog 不回填独立矩阵文件视为未闭环（四维链路断环亦然）。

### 门禁 5：独立验证与合入授权门禁（Independent Verification Gate）

- **约束规则**：开发者（人或 Agent）不得批准自己实现的测试结论、代码审查结论、合入或发布；“使用多个 Skill”不等同于独立验证。
- **强制动作**：测试验证和代码审查须由与开发角色不同的执行主体完成，并在 `07-review-report.md` 与 `09-changelog.md` 记录角色、执行主体、输入基线（commit SHA/文档版本）、结论与时间。
- **高风险变更**：涉及敏感用户数据（PII）、认证授权、生产 DB、模型/Prompt、对外接口破坏性变更或 P0 热修复时，除独立测试与 Review 外，必须由有授权的人类 Release Owner/领域负责人明确批准；Agent 不得替代该授权。

## 0.5 变更风险分级矩阵（唯一权威判定源）

> **强制规则**：全文任何提及"低风险""高风险""可合并角色""可豁免"之处，**一律以本节分级为唯一依据**，禁止 Agent 自行解释或另立标准。Agent 在任务开始时必须先在此表中判定风险等级，并把判定结果与依据写入 `09-changelog.md`「重要上下文」字段（§2.16.1 前置核对的一部分），作为后续角色独立性、平台/模型要求是否达标的判定基线。**未记录风险等级判定的变更，视为按 L3（最高等级）执行，不得自行降级。**

### 0.5.1 风险等级判定表

| 等级 | 判定依据（命中任一即为该级，就高不就低） | 典型场景 |
|---|---|---|
| **L0 极低** | 无逻辑变更：纯文档、注释、格式化、日志文案微调 | 修正错别字、调整代码缩进、补充注释 |
| **L1 低** | 需求优先级 P2，且不涉及核心业务模块、不涉及对外接口、不涉及§0门禁5高风险清单 | 内部工具函数优化、非核心页面样式调整 |
| **L2 中**（默认档） | 需求优先级 P0/P1，涉及核心业务逻辑，但未命中 §0 门禁5 高风险清单 | 常规功能新增/修改、内部服务间接口调整 |
| **L3 高** | 命中 §0 门禁5 高风险清单任一项：敏感用户数据（PII）、认证授权、生产 DB、模型/Prompt、对外接口破坏性变更、P0 热修复 | 核心业务逻辑变更、鉴权改动、生产数据订正、prompt 变更、对外 API 破坏性升级 |

### 0.5.2 风险等级 × Agent 独立性与平台要求矩阵

> 呼应 §2.1 Agent 角色分工：本表把"跨工具/跨模型厂商交叉验证"从可选实践，明确为按风险分级的**强制要求**，防止"同一 AI 厂商不同马甲互相验证"规避门禁 5 的实质。

| 等级 | 需求/计划角色 | 开发 Agent | 测试 Agent | Review Agent | 平台/模型要求 | 人类介入 |
|---|---|---|---|---|---|---|
| L0 | 可与开发合并 | Agent A | 可与开发合并（仅需留痕） | 可与开发合并（仅需留痕） | 无强制要求 | 无 |
| L1 | 可与开发合并 | Agent A | 必须独立子任务上下文（可同平台） | 必须独立子任务上下文（可同平台） | 无强制跨平台要求 | 无 |
| L2（默认） | 独立角色 | Agent A | 独立执行主体 + 独立子任务上下文（不同会话） | 独立执行主体 + 独立子任务上下文（不同会话） | 建议至少 1 环节跨平台/跨模型厂商（如开发用 Claude Code、Review 用 Codex） | 无（除非触发 §5 例外流程） |
| L3（高风险） | 独立角色 | Agent A | **必须**跨平台/跨模型厂商的独立 Agent | **必须**跨平台/跨模型厂商的独立 Agent，且与测试 Agent 所用平台/模型不同 | **强制**：开发、测试、Review 三方中至少覆盖 2 个不同底层模型厂商/平台 | **强制**：Release Owner 或领域负责人书面授权，Agent 不得替代（§0 门禁5） |

- **降级判定禁令**：L2/L3 变更不得以"任务简单""改动很小"为由自行降级到 L0/L1；如实际执行后发现风险等级判定有误，须在 changelog 中显式记录"风险等级修订"并说明理由，不得静默改判。
- **平台/模型证据格式**：凡命中"跨平台/跨模型厂商"要求的环节，角色签署表（§4）「执行主体/Agent 标识」字段必须按 §2.1.7 格式填写，缺失或格式不合规视为独立性证据不足，门禁 5 不通过。

## 1. 四维端到端需求追踪矩阵（RTVM 规范）

为确保“需求 -> 设计 -> 代码 -> 测试”环环相扣，项目统一使用以下编号规范与映射矩阵：

### 1.1 统一编号规范

**本表为全项目唯一编号权威源**：以下 9 种前缀此前分散定义在 §1、§2.6、§2.12、阶段 6 等多处，现统一归并于此；其余章节一律只引用本表，禁止另行定义新前缀或重复描述规则。

| 维度 | 标识前缀 | 说明 | 所在文档 |
|---|---|---|---|
| **需求规格 (Requirement)** | `REQ-xxx` | 业务需求、用户故事、功能约束 | `01-spec.md` |
| **设计决策 (Design)** | `DES-xxx` | 架构设计、数据结构、接口协议、时序决策 | `03-modification-plan.md` |
| **任务拆解 (Task)** | `TASK-xxx`（或沿用 `T1/T2/...`） | WBS 原子任务，每项可独立提交/回滚，标注依赖 | `03.5-tasks.md` |
| **代码实现 (Code / Change)** | `CHG-xxx` 或 `类名:行号` | 具体的源码类、方法、配置文件改动 | 源码 + `09-changelog.md` |
| **测试用例 (Test Case)** | `TC-xxx` | 单元测试、集成测试、回归测试用例 | `04-test-scripts.md` / `*Test.java` |
| **缺陷 (Bug)** | `BUG-xxx`（可选，见 §2.5 阶段6） | Bug 专用诊断编号，链接对应 CHG | `09-changelog.md` 分析/根因节 |
| **配置变更 (Config)** | `CFG-xxx` | 配置项/中间件/依赖参数变更（见 §2.6） | `06.5-deployment-config.md` |
| **数据库变更 (Database)** | `DB-xxx` | DDL/DML/索引/数据订正脚本（见 §2.6） | `06.5-deployment-config.md` |
| **遗留项 (Follow-up)** | `FU-xxx` | 待办/技术债（见 §2.12） | `06-delivery-summary.md` |

> **功能文档编号清单**（`docs/<feature>/` 统一前缀，缺号不补、新号递增）：
> `01-spec.md` / `01.5-rtvm-matrix.md`（四维 RTVM 总表）/ `02-code-impact-analysis.md` / `03-modification-plan.md` / `03.5-tasks.md` / `04-test-scripts.md` / `05-test-results.md` / `06-delivery-summary.md`（必含清单见 §2.5 阶段9.5）/ `06.5-deployment-config.md` / `07-review-report.md` / `08-supplement.md`（必含清单见 §2.5 阶段9.6）/ `09-changelog.md`
>
> **编号规则统一引用**：所有前缀均遵循同一套顺序规则——连续递增、不跳号、不重号、历史已分配编号不重排（详细规则见 §1.2，不在此处或其他章节重复展开）。

### 1.2 独立 RTVM 矩阵文件与编号顺序规范

**每个功能必须生成独立 RTVM 矩阵文件 `docs/<feature>/01.5-rtvm-matrix.md`**（带文档编号，独立成 md，不内嵌于其他文档）：

- **四维链路（一环一环）**：RTVM 从 **需求 → 设计 → 任务 → 测试** 四个维度逐环跟踪，一环对应一环——每个 REQ 必须能顺链走到 DES → TASK → TC，中间不可断环（设计须落到任务、任务须产出测试）。
- **矩阵表**：一张完整表汇总该功能**全部** REQ，列 = 需求编号 (REQ) / 需求简述 / 设计编号 (DES) / 核心设计方案 / 任务编号 (TASK) / 代码实现 (CHG/位置) / 测试用例 (TC) / 测试方法 / 验证状态（与 changelog §4 追踪矩阵映射列对齐）。
- **回填规则**：每次 CHG 完成后必须回填该文件的对应 REQ 行（TASK、CHG、TC、验证状态），禁止只更新 changelog 而不同步 `01.5-rtvm-matrix.md`（未闭环，§5 拦截）。
- **编号顺序规则（强制）**：
   1. 各类编号（REQ/DES/TASK/CHG/TC/CFG/DB/FU）各自**连续递增分配、不得跳号、不得重号**；
   2. **历史已分配编号不重排**（新编号只能继续递增，禁止为美观重排既有编号）；
   3. 矩阵表行**按 REQ 编号升序**排列；同一 REQ 多个 DES/TASK/CHG/TC 用 `/` 分隔，顺序 = 设计→任务→变更→测试（四维链路）。
   4. 需求若被后续 CHG 拆分/补充（如 CHG-006 新增 REQ-001~003 属于既有功能），新 REQ 继续递增，不并入旧编号。

- **扩展维度**：当变更涉及配置/DB（见 §2.6），在 `01.5-rtvm-matrix.md` 内追加第五维度映射子表（`CFG-xxx`/`DB-xxx` ↔ REQ ↔ DES ↔ CHG ↔ TC，模板见 §2.6.3），`06.5-deployment-config.md` 保留明细。

矩阵表模板（写入 `docs/<feature>/01.5-rtvm-matrix.md`）：

```markdown
# <功能名> RTVM 矩阵（四维闭环总表）

> 文档编号：01.5-rtvm-matrix.md
> 独立矩阵文件，规范依据：DEVELOPMENT_STANDARDS §1.1/§1.2 / 门禁 4。每次 CHG 完成后回填本表。
> 编号顺序：REQ/DES/TASK/CHG/TC 连续递增、历史不重排；行按 REQ 升序。
> 四维链路：需求(REQ) → 设计(DES) → 任务(TASK) → 测试(TC)，一环一环；CHG 为实现记录。


| REQ | 需求简述 | DES | 核心设计方案 | TASK | CHG/位置 | TC | 测试方法 / 脚本 | 验证状态 |
|---|---|---|---|---|---|---|---|---|
| `REQ-001` | 用户输入提取后需留存会话记忆 | `DES-001` | 输入处理完成后触发 memory 异步回写 | `T1` | `CHG-004` / `UserInputApplication.java:80-91` | `TC-001` | `UserInputApplicationParallelTest#testInputTrackRecordMemory` | ✅ PASS |
| `REQ-002` | 已回答的问题不再重复询问 | `DES-002` | LLM Context 注入完整问答历史对 | `T3` | `CHG-001` / `ConversationAgent.java:113-125` | `TC-002` | `ConversationAgentTest#testHistoryContainsAssistantRole` | ✅ PASS |
```

### 编号顺序核对表（§1.2 规则）

| 维度 | 编号范围 | 连续递增 | 说明 |
|---|---|---|---|
| REQ | REQ-001 ~ REQ-00N | ✅ | ... |
| DES | DES-001 ~ DES-00M | ✅ | ... |
| TASK | T1 ~ Tn（或 TASK-001 ~ TASK-00n） | ✅ | ... |
| CHG | CHG-001 ~ CHG-00k | ✅ | ... |
| TC | TC-001 ~ TC-00t | ✅ | ... |
| BUG/CFG/DB/FU | ... | ✅ | ... |

### 第五维度：配置/DB 映射子表（命中 §2.6 时）

> 模板见 **§2.6.3**（不在此重复）；`01.5-rtvm-matrix.md` 内追加 CFG/DB 映射子表，明细在 `06.5-deployment-config.md`。
> **扩展**：`01.5-rtvm-matrix.md` 与 `06.5-deployment-config.md`（CFG/DB 明细）各自成文，前者管追踪矩阵、后者管部署配置明细；第六维度告警见 §2.8。

## 2. 全局 Skill 交叉验证矩阵（Cross-Validation Matrix）

在软件生命周期的每个阶段，必须激活对应的 **核心技能组合（每个阶段 ≥ 2 个）** 进行交叉制衡与闭环：

### 2.1 Agent 角色分工、子 Agent 调度与独立性

> **Skill 是能力组合，Agent/人是责任主体；二者不得混淆。** 可使用 Cursor、Codex、Claude Code、Gemini 或人类开发者，平台名称不是独立性的证明。独立性以“不同执行主体 + 独立任务上下文 + 未修改被验证产物”为准。

| 角色 | 可承担的工作 | 禁止事项 | 必须交付/签署 |
|---|---|---|---|
| 编排 Agent（Orchestrator） | 任务拆解、子 Agent 调度与催办、状态跟踪、分歧升级发起 | 直接产出需求/设计/代码/测试/审查结论；替代任何角色签署；替代人类做高风险授权 | 调度日志（子任务分派与状态记录，写入 `09-changelog.md`「重要上下文」） |
| 需求 Agent / 业务 Owner | 澄清范围、验收标准、非功能与风险 | 修改实现；批准自己的需求变更 | `01-spec.md` 需求评审结论 |
| 架构/计划 Agent | 影响分析、方案取舍、任务拆解 | 编码；批准自己方案的实现 | `02` / `03` / `03.5` |
| 开发 Agent | 实现、开发者自测、修复 Review 问题 | 批准自身改动的测试、Review、合入或发布 | 源码、开发自测记录 |
| 测试 Agent | 依据 REQ/DES 独立设计用例、执行测试、报告缺陷 | 修改被测实现；批准合入 | `04` / `05-test-results.md` |
| Review Agent | 独立审查需求符合性、代码、安全、测试充分性与回滚 | 修改后审查/批准自己的改动 | `07-review-report.md` |
| Release Owner（人类） | 高风险变更的风险接受、合入/发布授权 | 将授权责任转交给 Agent | 发布/回滚记录 |

**子 Agent 规则（强制，AI 执行时逐条自查，不得跳过任一条）**：

1. 编排 Agent 必须为"需求/计划、开发、测试、Review"分别分派明确子任务，并在分派前依据 **§0.5 风险等级判定表** 确定本次变更等级；角色是否可合并、是否需要跨平台，一律以 §0.5.2 矩阵为准，**禁止编排 Agent 自行决定合并角色**。
2. 测试 Agent 必须先基于 `REQ/DES/TC` 和接口契约制定或审查测试，再读取实现；不得仅按开发 Agent 提供的实现说明写测试。
3. Review Agent 必须检查 diff、RTVM、测试证据和未动项，并使用独立上下文形成结论；不得只转述开发 Agent 的结论。
4. **独立性最低要求**：不同 Agent 至少使用不同会话/子任务上下文、不同执行主体标识；L2/L3 变更的跨平台/跨模型厂商要求见 §0.5.2，不得以"同一工具下的不同子 Agent"替代应达到的跨平台要求。若平台无法保证独立上下文，须改由人类或另一平台复核。
5. 每个 CHG 在 `09-changelog.md` 记录角色签署表（§4 模板）。无独立性证据，门禁 5 不通过。
6. Agent 仅可使用任务所需的最小权限；不得读取、输出或写入生产密钥/敏感用户数据。工具调用、测试命令和批准结论须可审计。
7. **Agent 标识强制格式**：角色签署表「执行主体/Agent 标识」字段必须填写 `平台名/模型标识 + 会话或任务ID`（示例：`Claude Code / claude-sonnet-4-6 / task-8f21`）。仅填"AI""Agent"或留空，一律视为独立性证据不足，门禁 5 判定为不通过，任务打回编排 Agent 重新指派。
8. **分歧升级机制**：测试 Agent 或 Review Agent 对同一 CHG 连续 2 次退回仍未达成一致时，编排 Agent 必须停止重复分派，转为升级人类介入仲裁（不得由编排 Agent 自行裁决对错）；仲裁过程与结论记入 `07-review-report.md`，并同步在 `09-changelog.md`「重要上下文」注明升级原因。
9. **完成状态强制原子化**：任一角色在自身环节未产出本节要求的"必须交付/签署"物之前，不得将该环节标记为"完成"；编排 Agent 汇总总体完成状态时，必须逐环节核对交付物是否存在（而非仅采信各 Agent 的口头汇报），核对方式见 §2.16.6。

|---|---|---|---|---|

## 2.5 分阶段产物与规格（Stage Deliverables & Specs）

> 每个阶段必须产出**明确产物**，且产物内容必须达到本节约定的**规格下限**（必含清单），未达规格不得进入下一阶段（对应 §3 检查清单）。所有产物命名统一放于 `docs/<feature>/` 目录，编号规则见 §1.1。

### 阶段产物验收标准总则（唯一权威定义，v2.19.0 起）

> 每个阶段的产物除满足"必含清单"（规格下限）外，必须通过该阶段正文「验收标准」行的**两层验收**；各阶段「验收标准」行为该阶段验收的**唯一权威定义**，其余章节只引用不另立。任一层未过，不得进入下一阶段：
>
> - **A 层（机器可验）**：结构标记类硬证据（编号体系、必含节、绑定标记）。可由 `scripts/agent-gate`（begin/pre-write/stop 门禁内置 A 层校验）或 CI（`check-standards-compliance.sh`）确定性校验。**AI 在声明该阶段完成前，必须先自行执行对应校验命令（如 `grep -c 'REQ-' docs/<feature>/01-spec.md`），并把命令与实际输出记入 09「变更执行检查清单」——只口头宣称"通过"而不附命令记录，视为未验收（§5 拦截）。**
> - **B 层（角色判定）**：质量与正确性判断项，由对应独立角色（测试 Agent / Review Agent，§2.1/§0.5.2）逐条核对并勾选、留 Agent 标识（§2.1.7）；**开发 Agent 不得自评 B 层通过**。
> - **勾选格式与落点**：每个阶段"声明完成"前，AI 必须把该阶段验收标准**逐条抄录**并标注 `[x]`/`[ ]`（§2.16.6 第 1 条适用），随 §3 清单归档 `09-changelog.md`「变更执行检查清单」；只写"已验收 / 已按规范产出"而不逐条列出，视为未验收，该阶段判定为未完成（§5 拦截）。

### 阶段 1：需求与规格定义（Doc-First）

- **产物**：`docs/<feature>/01-spec.md`（必须定义 `REQ-xxx`）
- **必含清单**：
   1. **需求梳理**：业务背景、问题描述、用户场景（用户故事）、现状与期望差距。
   2. **功能需求清单**：每条含 `REQ-xxx` 编号、需求描述、优先级（P0/P1/P2）、**验收标准（DoD）**。
   3. **非功能需求**：性能指标、安全约束、兼容性（前后端/多租户/接口向后兼容）、可用性。
   4. **边界与约束**：明确**不做**的事（Out of Scope）、依赖项、外部系统契约。
   5. **输入输出契约**：字段级定义（字段名/类型/是否必填/取值范围/示例），便于设计阶段直接转接口规格。
   6. **需求来源与评审**：需求来源（用户反馈 / 缺陷 / 评审结论 / 业务决策）、需求评审结论（可测性、优先级对齐、是否进入开发）。

- **需求变更管理（追加式）**：开发中需求变化时更新 `01-spec.md` 采用**追加式**——新增 `REQ-xxx` 或经 CHG 记录，**保留历史需求/决策原文，禁止覆盖旧记录**（与门禁 3 测试报告批次保留同精神）。
- **验收标准**：A 层——每条 REQ 含 `REQ-xxx` 编号与验收标准（DoD）字段（`grep -c 'REQ-' docs/<feature>/01-spec.md` 有输出）；B 层——需求 Agent/业务 Owner 确认每条 REQ 可测试、可追溯到 TC，无"模糊需求"（禁止"优化体验"类不可验证描述），留 Agent 标识（§2.1.7）。

### 阶段 2：业务与技术影响分析（先分析、后方案）

- **产物**：`docs/<feature>/02-code-impact-analysis.md`
- **必含清单（三维影响，缺一不可，v2.20.0）**：
   1. **业务影响**：受影响业务流程与用户场景（端到端旅程）、上下游系统与数据流、行业/合规约束（如金融、医疗、数据出境）、SLA 与体验阈值——从行业与业务视角回答"这个变更会改变什么业务行为、波及哪些流程"。
   2. **技术影响**：调用拓扑图（入口→链路→出口）、受影响类/文件清单、爆炸半径（Blast Radius）评估（含被波及的"看似无关"调用方与共享组件）。
   3. **风险与回滚**：风险矩阵（概率 × 影响表，高风险项附缓解措施）、回滚策略。
- **先分析后方案（强制顺序）**：本阶段未完成前禁止进入阶段 3 方案设计；方案未覆盖本阶段识别的影响面即打回（§5）。
- **验收标准**：A 层——02 含「业务影响」节与「风险」「回滚策略」关键词（`grep -q '业务影响' docs/<feature>/02-code-impact-analysis.md` 等三条全通过）；B 层——架构-计划 Agent 以**业务分析师 + 架构师双视角**核对：业务影响清单覆盖全部受影响流程与上下游、调用拓扑与受影响清单和代码实际一致（时点快照未改写，§2.15），留 Agent 标识（§2.1.7）。

### 阶段 3：方案设计与任务拆解（Design）

- **产物**：`docs/<feature>/03-modification-plan.md`（定义 `DES-xxx`）+ `docs/<feature>/03.5-tasks.md`
- **必含清单**（按功能规模取用，新增功能全项必含）：
   1. **架构设计**：分层/模块归属、依赖方向、新增组件说明。
   2. **接口/API 设计**：HTTP 方法、路径、**请求/响应字段表**（字段/类型/必填/说明/示例）、状态码与**错误码**定义、示例报文。
   3. **流程设计**：时序图/流程图（mermaid 或 UML），标注正常流、分支流、异常流、降级流。
   4. **数据设计**：表结构变更、索引、缓存策略（key/过期/容量）、事务边界。
   5. **技术选型与决策记录（多方案强制对比，v2.20.0）**：**至少 2 个候选方案**的对比矩阵（维度：实现复杂度 / 性能 / 可维护性 / 团队熟悉度 / 业界成熟度与前沿性 / 风险与回退成本），结论必须论证「为何该方案最适配当前业务场景」（含规模、团队能力、演进路径）；选用前沿/未普及技术须额外标注试验风险与回退路径；决策背景入 ADR。**禁止无对比直接定方案**（§5）。
   6. **兼容性与影响**：对既有调用方（Controller/WS/前端）的兼容措施；破坏性变更的弃用策略见 §2.13.3。
   7. **任务拆解（专业项目管理标准，v2.20.0）**：WBS 原子任务（每项可独立提交/回滚），每任务标注**依赖关系与关键路径、可并行组、粗粒度工作量估算、里程碑检查点、完成标准（DoT：可验证的退出条件）**，关键路径任务预留风险缓冲；**每个 CHG 必须在 `03.5-tasks.md` 追加任务行（T-next）或显式标注"CHG 直接实施（未拆任务，理由）"**，禁止 CHG 无任务归属（防四维链路断环）。

- **验收标准**：A 层——`grep -c 'DES-' docs/<feature>/03-modification-plan.md` 有输出，03 含「备选/选型」对比内容（`grep -qE '备选|选型' docs/<feature>/03-modification-plan.md`），且 03.5 含 T 任务行（含依赖/里程碑标注）或 CHG 豁免标注；B 层——计划角色以**架构师 + 项目经理双视角**确认：每个 `DES-xxx` 可向下映射到代码（CHG）与测试（TC）、技术选型有 ≥2 候选对比且业务适配论证成立、任务拆分含关键路径与里程碑、接口变更给出前后兼容说明，留 Agent 标识（§2.1.7）。

### 阶段 4：测试脚本先行（Test-First）

- **产物**：`docs/<feature>/04-test-scripts.md`（定义 `TC-xxx`）
- **必含清单**：测试命令（JDK/Maven 全量命令）、用例矩阵（TC 编号/场景/输入/期望断言/**覆盖维度**/覆盖的 REQ-DES）、TDD 红→绿运行方式；测试 Agent 的独立性声明（§2.1）。
- **覆盖维度矩阵（测试专家标准，逐维度设计用例，v2.20.0）**：功能正常流 / **业务场景**（端到端用户旅程，按 01-spec 用户故事）/ **逻辑分支**（条件、循环、状态迁移）/ 边界值与空值 / 异常与降级兜底 / **数据组合与状态**（多数据形态、并发状态，如适用）/ **安全**（越权、注入、敏感数据，如适用）/ **兼容性**（接口前后兼容、多端）/ **回归**（受影响既有功能）。L0/L1 小变更可裁剪不适用的维度，但**必须逐维度显式标注"不适用，理由"**，禁止静默裁剪（§2.16.6 第 3 条）；变更时按门禁 2 变更测试策略判定**复用 vs 新增**（打点必须断言内容，合入前跑全量回归）。
- **验收标准**：A 层——`grep -c 'TC-' docs/<feature>/04-test-scripts.md` 有输出，用例矩阵含「覆盖维度」与「覆盖的 REQ-DES」列（`grep -q '覆盖维度' docs/<feature>/04-test-scripts.md`）；B 层——测试 Agent 以**测试专家视角逐维度核对**：九类覆盖维度均有用例或显式"不适用"标注（无未声明缺口）、正常/边界/异常全覆盖（门禁 2）且复用 vs 新增判定留痕，独立性声明附 Agent 标识（§2.1）。

### 阶段 5：代码实现（Coding）

- **产物**：源码（在关键改动处标注 `CHG-xxx`）+ 对应测试类 `*Test.java`
- **中文注释规格（强制，逐条执行）**：
   1. **类/接口注释**：`@author` + 类职责一句话说明（如 `/** 必填信息收集收敛拦截（CHG-006 R1）：... */`）。
   2. **方法注释**：对公共 API、复杂业务逻辑或契约变化的方法说明职责、`@param`、`@return`、`@throws` 与业务约束；不要求为简单私有方法机械补全 Javadoc。改动处以最小必要范围标注 `CHG-xxx`。
   3. **关键逻辑 WHY 注释**：不解释"做了什么"（WHAT），必须解释"为什么这么做"（WHY）——业务原因、边界取舍、防坑点。
   4. **契约字段注释**：DTO/VO 新字段必须注释含义与可空性（如 `sessionId（可空，CHG-006 R2）`）。
   5. **降级/兜底路径注释**：异常分支必须注明触发条件与降级行为。

- **编码约定**：沿用既有代码风格；防御性编程（判空/异常不吞掉）；敏感信息不入日志；新增依赖需说明理由并做供应链审核（§2.13.2）。
- **ReAct 微循环（v2.21.0，每次源码修改强制）**：每次改动前 **Thought**——分析当前状态、修改目标与影响面（引用 02 三维影响分析，含被波及的调用方与共享组件，§2.16.2 铁律）；改动后 **Observation**——运行受影响测试与验证命令并记录实际输出。**禁止"上来就改代码"**（§5 严重违规）。
- **验收标准**：A 层——关键改动处含 `CHG-xxx` 标注（`grep -rn 'CHG-' <变更源码>` 有输出）；B 层——Review Agent 审查："无 WHY 注释"或"注释只复述代码"一律打回（见 §5 Anti-Patterns），留 Agent 标识（§2.1.7）。

### 阶段 6：缺陷诊断与根因推导（Bug 专用）

- **产物**：诊断分析报告（可并入 `09-changelog.md` 的"分析/根因"节）；缺陷可编号 `BUG-xxx`（可选，链接 changelog CHG，标注严重度 P0/P1/P2）
- **必含清单**：复现步骤、完整调用链（入口→类→方法→分歧点）、正常 vs 异常链路对比、代码行列级根因表、排除其他假设的理由。
- **验收标准**：A 层——09 CHG「分析/根因」节含代码行列级根因表与 BUG-xxx 编号（如启用）；B 层——测试/Review 角色复核根因含"排除其他假设"论证，复现步骤可独立重放。

### 阶段 7：运行测试与证据闭环

- **产物**：`docs/<feature>/05-test-results.md` + 真实控制台输出
- **必含清单**：运行环境（JDK 版本、命令）、脱敏测试摘要（含 Tests run/Failures/Errors/Time/退出码）及受控原始日志制品链接、用例明细表、**批次保留**（门禁 3：独立批次小节 §N，不覆盖历史批次；**每批次必含四要素清单：[变更前后用例数] [受影响] [新增] [复用]**）、覆盖率（**新增代码行 ≥70%**，JaCoCo，如适用）、命中非功能性能指标时附**性能/容量验证**、测试 Agent 独立性声明。
- **验收标准**：A 层——05 新增批次 §N 绑定 CHG 且含四要素清单与 Tests run/Failures/退出码摘要；B 层——测试 Agent 确认证据完整（覆盖率 ≥70% 如适用、性能验证如命中），历史批次未被覆盖，留 Agent 标识（§2.1.7）。

### 阶段 8：代码审查与安全门禁

- **产物**：`docs/<feature>/07-review-report.md`
- **必含清单**：审查范围（文件清单）、发现的问题分级（严重/中/低）、需求符合性、测试充分性、安全/隐私、并发与回归隐患、回滚可行性、评审结论（通过/有条件通过/退回）及 Review Agent 独立性声明。
- **验收标准**：A 层——07 含「评审结论」节（通过/有条件通过/退回）与 Review Agent 标识；B 层——独立 Review Agent 出具结论，问题分级（严重/中/低）齐全，开发 Agent 不得自评（§0.5.2）。

### 阶段 9：交付与追踪闭环

- **产物**：`docs/<feature>/09-changelog.md`（含 `CHG-xxx`）
- **必含清单**：§4 必填字段 + **回填所属功能独立 RTVM 矩阵文件 `01.5-rtvm-matrix.md`**（§1.2，含验证状态、编号顺序核对与四维链路）；**回写 `03-modification-plan.md` 正文**（新增/更新对应"修改点"节，禁止只更新 DES 登记表不更新正文——防方案文档滞后）；分支/PR 协作规范见 §2.13.1，发布/回滚见 §2.7。
- **验收标准**：A 层——09 CHG 含 §4 必填字段与「变更执行检查清单」归档，`01.5-rtvm-matrix.md` 已回填且 03 正文已回写；B 层——Review 角色核对 RTVM 四维链路（REQ→DES→TASK→TC）无断环。

### 阶段 9.5：交付总结（`06-delivery-summary.md`，补全缺失规格）

## 2.6 部署、配置与数据库变更规范（Deployment / Config / DB Change Standard）

> **触发条件（任一命中即必须遵守本节）**：改动了配置文件、新增了配置项、调整了中间件/缓存/依赖，或存在任何数据库变更。**禁止"代码改了、配置靠口口相传"、禁止"直接手改生产库"。**

### 2.6.1 适用范围（Scope）

凡涉及以下任一项的变更，除走 REQ → DES → CHG → TC 常规流程外，**必须**额外维护独立部署配置文件 `docs/<feature>/06.5-deployment-config.md`：

| 类别 | 典型对象 | 例子 |
|---|---|---|
| **项目配置** | `application.yml`/`application-*.yml`/`bootstrap.*`/`*.properties`/`pom.xml`/`logback-*.xml` | observability 开关、新增依赖、日志级别 |
| **Nacos / 注册中心** | dataId / group / 命名空间 / 灰度发布 / 动态刷新 | 新增 dataId、修改 group、配置灰度 |
| **Redis** | key 设计、过期时间、容量、序列化方式、连接池、分布式锁 | 新增缓存 key、TTL 调整 |
| **本地缓存** | Caffeine 等内存缓存 | maximumSize / expireAfterAccess 调整 |
| **中间件/其他** | 消息队列、线程池、Druid 连接池、第三方 SDK | 线程池容量、慢 SQL 阈值、SDK 版本 |
| **数据库变更** | DDL / DML / 索引 / 存储过程 / 数据订正 | 建表、加列、加索引、INSERT 数据脚本 |

### 2.6.2 必含产物：`06.5-deployment-config.md`

每个命中 §2.6.1 的变更，必须在该文档中追加记录。**必含清单**：

1. **配置变更记录表**：配置项全名（key）/ 变更前值 / 变更后值 / 生效范围（环境、租户、生效方式：重启 or 热更新）/ 变更原因（关联 `REQ`/`DES`/`CHG`）。
2. **数据库变更脚本规范**：
   - 脚本编号 `DB-xxx`，文件名约定 `V{序号}__{描述}.sql`（如 `V1__add_feature_config.sql`）。
   - 优先提供迁移脚本与回滚/前向修复脚本。若 DDL、数据订正或已对外暴露的数据无法安全无损回滚，必须明确标注**不可逆**，给出备份/校验、灰度或停机窗口、前向修复方案，并由 Release Owner 批准。
   - 脚本必须可重复部署：使用版本化迁移工具时依赖其版本记录保证一次性执行；仅对语义安全的对象使用 `IF NOT EXISTS` / `ON DUPLICATE KEY` / 先查后插。禁止用幂等语句掩盖环境漂移，执行前后须校验 schema/数据状态。
   - 禁止手改生产库；任何数据变更必须走版本化脚本并记录执行人 / 时间 / 环境。

3. **矩阵关联（第五维度映射）**：每条配置/DB 变更必须映射到 REQ / DES / CHG / TC（见 2.6.3）。
4. **验证方式**：该配置/DB 变更的验证命令或 SQL 校验语句（如 `mvn test`、`SHOW INDEX`、`SELECT count(*)`），结果入 `05-test-results.md`。
5. **敏感信息红线**：密码 / token / AK-SK 等**严禁**写入 git 与日志明文；走 Nacos 加密 / 环境变量 / 密钥管理（如 1Password）；日志脱敏。

### 2.6.3 配置/DB 变更追踪矩阵（CFG/DB 映射模板）

RTVM（§1.2）在此场景**扩展第五维度**。以下映射表与 RTVM 并列维护：

```markdown

| CFG/DB 编号 | 变更项（key/脚本） | 范围/环境 | 关联需求 | 关联设计 | 关联变更 | 关联测试 | 验证状态 |
|---|---|---|---|---|---|---|---|
| `CFG-001` | `feature.observability.enabled=true`（application.yml） | dev/test | `REQ-003` | `DES-003` | `CHG-002` | `TC-003` | ✅ PASS |
| `DB-001` | `V1__add_feature_config.sql` | 全部环境 | `REQ-003` | `DES-003` | `CHG-002` | `TC-004` | ✅ PASS |
```

### 2.6.4 记录更新要求（Changelog 联动）

- `09-changelog.md` 的**「方案」节必须列出全部配置与 DB 变更清单**（表：CFG/DB 编号 / 变更项 / 目的），并链接 `06.5-deployment-config.md`。
- **「未动项」节**必须声明未变更的关联配置/库表（如"未调整 Druid 慢 SQL 阈值"），防止后人重复排查。
- 配置/DB 变更若无对应 changelog 记录，视为**未闭环**（触发 §5 违规拦截）。

## 2.7 发布与上线流程规范（Release & Deploy Standard）

> **触发条件**：任何 CHG 合入主分支后进入发布，或涉及生产环境变更（代码 / 配置 / DB / 模型）。规范只到"提交"是不够的——上线后才发现的问题成本最高。

### 2.7.1 环境顺序与发布检查单

- 强制环境顺序：`dev → test → staging（如有）→ prod`，禁止跨环境跳过（热修复例外见 §2.11）。
- **发布检查单（Release Checklist）**，全部通过才可发布：
   1. 代码已具备合入条件，`09-changelog.md` §4 必填字段完整，RTVM / CFG-DB 矩阵闭环（门禁 4），并通过独立测试、Review 和必要授权（门禁 5）。
   2. 全套件测试通过，证据在 changelog（门禁 3）。
   3. 配置/DB 变更已在 `06.5-deployment-config.md` 记录，且**目标环境已应用**（§2.6）。
   4. AI/LLM：模型/endpoint 目标环境可用性验证通过（§2.9.1）。
   5. 监控/告警已配置，且**上线冒烟验证观测确实有数据**（§2.8）。
   6. 回滚预案就绪：代码 tag、配置旧值、DB 回滚脚本（§2.6.2）。

- 发布动作本身记录到 changelog「发布与回滚记录」字段（§4 第 8 要素）。

### 2.7.2 上线冒烟验证（Post-Deploy Smoke Test）

- 发布后必须对**受影响链路**执行冒烟：主流程至少调用一次，验证返回正确 + 日志/观测有数据。
- 冒烟命令/步骤与结果写入 `05-test-results.md` 的发布节。
- **冒烟失败 → 立即进入回滚（2.7.3）**，禁止带病观察。

### 2.7.3 回滚标准与决策

- 触发回滚判定：P0 功能不可用、数据错误、性能劣化超基线、安全事件。
- 决策人：Release Owner；紧急情况下由当班负责人先处置，并在事后补齐 Release Owner/技术负责人确认。开发 Agent 或当次 CHG 执行人可提出建议，但无权单独接受生产风险。
- 回滚内容：代码回退 tag + 配置恢复旧值 + DB 回滚脚本（成对，§2.6.2）。
- **观察窗口**：发布后 24h 观察期，重点监控告警、错误率、慢查询；观察期结论记录回 changelog。

## 2.8 监控、告警与可观测门禁（Monitoring / Alerting Gate）

- **触发条件**：新增/修改任何用户可见链路、异步任务、外部依赖调用。
- **强制动作**：
   1. 链路必须接入可观测（结构化日志 / 独立 logger / 追踪 trace），并**验证观测确实产出数据**——防"观测 0 字节"重演（典型教训：HTTP 链路未接 tracer，日志文件为空且无人发现）。
   2. 定义关键指标与告警：错误率、耗时 P95、慢 SQL、外部依赖（LLM）失败率。
   3. **未定义告警的 P0 链路禁止上线**；告警阈值与接收人写入发布检查单。

- **产物**：告警配置清单（告警项 / 指标 / 阈值 / 接收人）记入 `06.5-deployment-config.md` 或 changelog 发布节。

## 2.9 AI/LLM 专项规范（AI / LLM Standard）

> 涉及 AI/LLM 调用的链路属于高风险变更面。除通用门禁外，必须遵守：

### 2.9.1 模型与端点可用性（防 endpoint 404）

- 任何调用外部模型服务（如 OpenAI、Ark、Bedrock 等）的链路，上线前必须验证：模型 endpoint 存在、key 有权限、额度充足。
- 模型 ID / endpoint 属于**配置变更**：改模型必须走 §2.6（06.5 记录 + CFG 矩阵），并提供**目标环境**验证证据。
- 典型教训：生产配置的模型 endpoint 在当前账号下 404，测试环境临时换模型验证通过——**上线前必须在目标环境实测，禁止只靠本地/其他账号验证**。

### 2.9.2 提示词（Prompt）变更门禁

- prompt 视为代码：改 prompt = 改逻辑。必须：① 走库（禁止代码写死）；② 升版本（INSERT 新行 status=1 + 旧行 status=0）；③ changelog 记录（含 CFG/DB 矩阵）。
- prompt 变更必须附带影响面说明与验证（TC 覆盖或人工核验样例）。

### 2.9.3 AI 安全与幻觉防护

- 信息不足必须**引导补充而非臆测**（提示词设计应内建该原则）；输出按产品要求含免责提示。
- 禁止 AI 输出作为唯一决策依据：关键结论保留人工确认路径。
- 降级路径（模型不可用 / prompt 缺失 / 解析失败 / 空响应）必须定义并验证（门禁 2 异常流）。

### 2.9.4 敏感数据隐私与脱敏（PII）

- 用户输入 / 会话文本属**敏感隐私数据**：禁止未脱敏写入日志、明文入 git、输出到非授权终端。
- 发送外部 LLM 前确认授权边界与数据保留策略；日志落盘需脱敏（姓名 / 电话 / 住址 / 证件号 / 邮箱等 PII 字段）。
- 违反视为 🔴 严重违规（§5）。

### 2.9.5 成本控制

- 外部 LLM 调用关注 token 成本：新增/高频调用在 03-plan 说明量级预估；超长上下文用压缩策略（如上下文压缩组件、历史摘要截断等）。

## 2.10 测试数据与环境隔离（Test Data & Environment Isolation）

- **强制规则**：
   1. 测试脚本**禁止写生产库/生产环境数据**；数据写入必须走测试库或测试租户。
   2. 测试数据脚本必须声明：执行环境、影响表、幂等性、**清理步骤**（执行后清理测试插入数据）。
   3. 集成测试使用独立配置（如 `profiles.active=test`）与独立数据源。
   4. 含 DB 写入的测试脚本在 `04-test-scripts.md` 明示，写入动作留痕。

- 已知教训（曾有数据初始化脚本直写业务库插入配置数据）：合法的数据初始化脚本也必须显式登记为 `DB-xxx` 并含清理/回滚说明（06.5 §2），禁止"静默写库"。

## 2.11 热修复快速通道（Emergency Hotfix）

- **适用**：生产 P0 事故（服务不可用 / 数据损坏 / 安全事件），走标准全流程会扩大影响面。
- **规则**：
   1. 门禁允许**并行**执行（先修 + 事后补文档），但以下**不可豁免**：日志留痕（changelog 事后 24h 内补齐）、回滚预案、根因分析（§2.5 阶段 6）。
   2. 流程：确认事故 → 最小修复 → 冒烟（§2.7.2）→ 发布 → 24h 内补全 changelog / RTVM / 06.5 → 根因复盘。
   3. 每次热修复必须触发一次 §2.12 遗留项/复盘记录，防同类再发。

## 2.12 遗留项闭环管理（Debt & Follow-up Closure）

   3. 关闭时在 changelog 记录（关联 CHG）。

## 2.13 协作、依赖供应链与接口生命周期（Collaboration / Supply Chain / API Lifecycle）

### 2.13.1 分支与 PR 协作

- 分支命名：`{yyyyMMdd}-{feature|bugfix}-{简述}`（如 `260803-bugfix`）；禁止直接向主分支提交代码。
- 合入主分支必须经 code review（§2.5 阶段 8）并留 `07-review-report.md` 结论；重大变更需 ≥2 个审查视角（含 skill 交叉验证）。
- 开发、测试、Review 必须遵守 §2.1 独立性；PR/合入记录必须关联独立测试与独立 Review 的结论。高风险变更还须有 Release Owner 的明确授权。

### 2.13.2 依赖供应链

- 新增/升级依赖（pom 等）必须：说明理由（替代方案对比）、确认许可证与 CVE 风险（无扫描工具时人工检索）、**锁定版本**（禁止无版本号依赖）。
- 第三方 SDK（含 AI SDK）升级视为配置/依赖变更，记入 06.5。

### 2.13.3 接口生命周期与弃用策略

- 对外接口变更遵守向后兼容：新字段只增不改语义；禁止静默改变量类型 / 单位 / 默认值。
- 破坏性变更必须：提供过渡期（旧接口保留 ≥1 版本并标记 deprecated + 弃用日期）；接口版本化（如 `/api/v2`）为可选方案。
- 弃用/移除在 changelog 显式记录，并在 `01-spec.md` 标注。

### 2.13.4 自动化质量门禁与例外

- CI/PR 必须自动执行并留存结果：编译、受影响模块测试、全量回归、覆盖率、静态分析、依赖/CVE 与许可证检查、密钥泄露扫描；适用时增加接口契约、性能和迁移校验。自动化通过不替代门禁 5 的独立判断。
- 所谓"全量回归"必须写明命令、范围、基线版本与结果；若因环境/时限不能运行，CHG 必须标记为**未完成/有条件通过**，列出风险、补偿措施、责任人和完成期限，禁止写成"测试通过"。
- 任何门禁例外仅可由 Release Owner（高风险须技术/领域负责人共同）书面批准，记录适用范围、原因、风险、补偿措施、到期时间；例外到期自动失效，不能被 Agent 自行批准。

## 2.15 文档更新与变更逻辑（防覆盖 / 防丢失）

> 不同交付物有不同的更新语义：**有的只能追加、有的可作活文档改状态、有的是时点快照不可改、有的是不可变记录**。明确如下，防止"覆盖丢历史"或"该更新的没更新"。

| 文档 | 更新策略 | 追加式 | 活文档（可改状态/正文） | 不可变 / 时点快照 | 历史保存处 |
|---|---|---|---|---|---|
| `01-spec.md` | **追加式** | ✅ 新 REQ/DES/决策追加 | - | 既有 REQ 行/决策原文不改写 | §14/§16 追加 + changelog |
| `01.5-rtvm-matrix.md` | 回填 + 维护记录 | ✅ 新 REQ 行追加 | ✅ 验证状态列可更新 | 行内历史不回退 | 维护记录表（§4） |
| `02-code-impact-analysis.md` | **时点快照** | - | - | ✅ **分析时点基线，不随后续 CHG 改写**（后续影响以 03 正文 + changelog 为准） | changelog / 03 正文 |
| `03-modification-plan.md` | **活文档（回写正文）** | - | ✅ 修改点节随 CHG 更新（覆盖旧正文 OK） | - | 历史由 changelog 各 CHG「方案」+ 01.5 维护记录承担 |
| `03.5-tasks.md` | 活文档 + 追加 | ✅ 新 T 任务追加 | ✅ T 状态列更新 | - | 状态列 |
| `04-test-scripts.md` | 追加式 | ✅ 新 TC / § 追加 | ✅ 既有 TC 状态（✅）更新 | - | - |
| `05-test-results.md` | **批次追加（门禁 3）** | ✅ 每批次独立小节 §N | - | ✅ 历史批次原文/状态不可覆盖 | 各批次原文 |
| `06-delivery-summary.md` | 活文档 + 追加 | ✅ FU 追加 | ✅ FU 状态 / 上线检查单更新 | - | FU 状态列 |
| `06.5-deployment-config.md` | **配置追加式** | ✅ **同一 key 再次变更必须新增 CFG 行（CFG-next），不改写旧行** | - | ✅ 旧 CFG/DB 行不改写 | CFG/DB 记录表 |
| `07-review-report.md` | 追加式 | ✅ 新审查节追加 | - | ✅ 旧结论保留；作废须在追加节显式声明 | 追加节 |
| `08-supplement.md` | 追加式 | ✅ | - | - | - |
| `09-changelog.md` | **条目不可变** | ✅ 新 CHG 插顶部（时间倒序） | - | ✅ **已闭合 CHG 禁止改写**（现象/根因/方案/验证结果）；修订须在当条内加「修订说明」或开新 CHG | 各 CHG 条目 |

**硬性规则**：
1. **批次绑定变更**：`05-test-results.md` 每个批次小节标题必须标注对应 CHG / 变更编号（如 `§N：CHG-XXX`）；里程碑批次（如首次 Maven 套件）标注 TASK 里程碑。
2. **可改 ≠ 可丢**：活文档（01.5/03/03.5/06）允许更新状态/正文，但**任何状态翻转或正文覆盖都必须能在 changelog 或维护记录中追溯到**；否则视为覆盖丢失（§5 拦截）。
3. **配置记录只增**：06.5 配置/DB 记录表**只追加**，同一 key 再变更新增 CFG 行（`CFG-next`），旧行保留（前值→后值对照），禁止原地改旧行。
4. **changelog 只增不改**：已闭合 CHG 不可变；补丁/修订开新 CHG 或当条「修订说明」。

**ReAct 执行铁律（v2.21.0，全局分析强制）**：执行主线的每一步、以及阶段 5 的每一次源码/文档修改，必须按 **Thought → Action → Observation** 三段式推进，禁止跳过 Thought 直接 Action（"上来就改代码"）：

- **Thought（先分析）**：动手前陈述当前状态、目标与**全局影响判断**——必须引用阶段 2 三维影响分析（业务/技术/风险，§2.5）与 §2.16.1 背景调研结论，明确本次动作波及的调用方、流程与业务；**不得只看本次待改文件**。
- **Action（后执行）**：基于 Thought 结论调用工具/执行变更（代码/文档/命令）；Action 范围不得超出 Thought 分析覆盖的影响面，执行中发现新影响点必须先回到 Thought 补分析再继续。

### 2.16.6 防遗漏/防跳过强制执行规则（AI 专用红线）

> 本节专门约束 AI 执行本规范时最常见的失效模式——**不是不知道规则，而是在长任务/多步骤中悄悄省略、用摘要代替逐项核对、或在自认为"大体完成"时提前标记完成**。以下规则优先级高于"效率""简洁"等一般性倾向，AI 不得以任务复杂、上下文长、时间紧为由自行减免。

1. **逐项复述强制**：AI 在声称任一阶段/门禁/DoD 完成前，必须把对应清单（§2.16.3 DoD 或 §2.16.4 自检，或所属阶段的 §2.5 必含清单）的**每一项原文**列出并逐条标注 `[x]`/`[ ]`，禁止仅用一句话总结"已按规范完成"来代替逐项清单；无逐项清单佐证的完成声明一律视为无效。
2. **缺失即未完成**：清单中任一项没有对应产物/证据，该环节即为未完成，AI 不得将整体任务标记为"完成"，必须继续执行剩余项，或在无法继续时明确报告"未完成 + 阻塞原因 + 需要的外部输入"。**不允许因为大部分已完成、只差一两项，就整体标记为完成。**
3. **禁止静默降级/静默跳过**：AI 不得因为某一步骤"看起来不重要""与本次改动关系不大"就自行跳过而不声明；跳过某一项必须显式写出该项编号与跳过理由，并说明是否属于 §2.5 所述"未命中"（如未命中配置/DB 变更类别，则该项本就不适用，需写明"未命中，不适用"而非直接不提）。
4. **禁止"部分执行当全部执行"**：例如全量回归只跑了受影响模块，不得在清单勾选"全量回归通过"，必须如实标注"部分回归"并按 §2.13.4 走"未完成/有条件通过"流程。
5. **上下文预算不足的显式声明**：如果 AI 判断当前对话/任务的可用步骤数、token 预算不足以完成全部 10 阶段 + 5 门禁，必须在早期（不晚于阶段 3 完成时）向编排 Agent 或人类明确声明"预计无法在当前会话内完成全部流程，建议分批执行，已完成到 ___ 阶段"，而不是在结尾突然发现遗漏、或悄悄压缩后续阶段的执行深度（如把"运行测试"简化为"预期测试会通过"）。
6. **完成声明的最终格式**：AI 在一次变更的最终交付消息中，必须包含以下三部分，缺一不可：
   ① 本次风险等级判定（§0.5）及理由；
   ② §2.16.3 DoD 全部条目逐条 `[x]`/`[ ]` 结果（不可用"以上均已完成"代替逐条罗列）；
   ③ 如有任何 `[ ]` 未完成项，列出后续处理人与预计完成方式。
7. **人类/编排 Agent 的复核义务**：编排 Agent 或人类在采信任一子 Agent 的"已完成"结论前，必须按第 1 条抽查其逐项清单是否真实存在对应产物（如 05-test-results.md 是否真的有本批次控制台输出），不得仅采信文字汇报；发现清单与实际产物不符，按 §5 Anti-Patterns"口头宣称测试已通过"同等严重级别处理。

### 2.17 变更管线自动化扩展（传动机制、事故重入、自主权分级、自测试）

> 本节把 §2.16 执行主线从"人/AI 逐阶段驱动"扩展为"产物驱动"：产物合入即确定性触发下一阶段的骨架派发（传动机制）；生产事故作为新的意图重入管线（§2.5 阶段 6 的自动化入口）；一切自动化动作按环境分级授权；治理配置自身必须通过 golden-case 回归测试。**铁律：自动化只生成骨架与登记，不生成产物正文**（防臆造，同 §2.16.6 精神；违者触发 §5）。

> **外部研究依据（v2.18.0）**：本节「状态外置、只信磁盘」的设计有实证支撑——CIKM '26 论文《The Compaction Cliff in Long-Running AI Agent Memory》（[arXiv:2608.22752](https://arxiv.org/abs/2608.22752)）实测生产级 Agent 的上下文压缩：Sonnet 4.6 的 /compact 一轮后安全规则仅存 53%、五轮后 10%；且去掉验证器的系统会「报告 100% 保留、实际静默丢失 57% 约束」。流程侧依据（意图漂移、决策路径不可复盘、事故不回流）见 Anthropic《[The AI-Native SDLC Playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)》。故本规范铁律：治理状态一律外置为磁盘产物（不依赖 Agent 记忆）；写盘后必须以 shell 级磁盘验证（`grep -c` / `wc -l` / `git diff`）确认落盘，不得采信工具返回值或 Read 缓存（AGENTS.md 红线）；门禁只读磁盘与 git 状态，不采信 Agent 声明。

> **管线入口产物 `00-intent.md`**：每个变更在进入阶段 1 之前必须先落 `00-intent.md`（问题 / 预期结果 / 受影响用户与系统 / 约束 / 开放问题 / 意图澄清记录，模板见 skill 资源 `intent.md`）。阶段 1（门禁 1）将其转写为 `01-spec.md` 的 `REQ-xxx`；无 `00-intent.md` 的变更视为无意图变更，可执行门禁（`agent-gate begin`）拒绝放行。`00-intent.md` 为追加式文档（§2.15），可由需求角色、人类或监控系统创建；开放问题未全部关闭前不得进入阶段 3。

#### 2.17.1 传动机制（Artifact Pipeline）

1. **触发规则**（确定性、基于产物路径，不依赖自然语言判断）：
   - `01-spec.md` 合入主干 -> 自动创建 `automation/<变更ID>-scaffold` 分支，按阶段顺序派发 `02-code-impact-analysis.md`、`03-modification-plan.md` 与 `04-test-scripts.md` 骨架并开 PR；
   - `09-changelog.md` 合入主干 -> 自动开发布检查单 issue（§2.7.1 六项：回滚预案、配置核对、DB 脚本核对、监控告警、灰度计划、发布授权）。
2. **骨架约束**：骨架只含章节标题与待填注释，禁止预生成方案/测试内容（防臆造）；正文填写仍由方案/测试角色经门禁 1/2 完成，自动派发不豁免任何门禁。
3. **频控**：目标分支已存在即跳过，防止重复触发。
4. **平台无关性**：参考实现为 GitHub Actions（skill 资源 `github-artifact-pipeline.yml`）；GitLab 等平台用等价 CI 触发规则 + 平台 API 实现同一语义，**语义以本节为准而非以具体平台为准**。

#### 2.17.2 事故重入管线（Incident -> Intent）

1. **闭环语义**：事故 = 未被记录的意图。任何生产事故（告警、故障、SLO 违约）必须转化为一个新变更的 `00-intent.md` 骨架（编号 `BUG-<UTC 时间戳>`），禁止"修完不留痕"；事故处置随后走 §2.5 阶段 6 诊断，生产事故同时遵守 §2.11 热修通道。
2. **触发方式**：监控/告警系统调用代码托管平台的事件接口（如 GitHub `repository_dispatch`，类型 `incident`）并附带告警元数据（source / metric / current / threshold / severity / triggered_at / detail_link）；参考实现见 skill 资源 `github-incident-to-intent.yml`。
3. **频控与注入**：目标分支已存在即跳过（防告警风暴）；元数据以「自动注入，勿删」节写入骨架，接手者补全六节内容后按 §2.16 主线执行。
4. **自主权上限**：本管线只创建文档骨架与 PR（A2 级，见 §2.17.3），不自动修复、不自动合入、不触碰生产环境。

#### 2.17.3 分环境自主权分级（自动化动作授权矩阵）

| 级别 | 动作类别 | 示例 | 授权环境 |
|---|---|---|---|
| A0 | 只读观察 | 查询 diff、输出度量（§2.17.5） | 任意环境 |
| A1 | 登记 | 创建 issue / 评论 / 打标签 | 任意环境 |
| A2 | 骨架 | 创建分支 + 骨架文件 + PR | 任意环境（合入仍需人类/角色审查） |
| A3 | 内容 | 填充产物正文、修改代码 | 仅本地/沙箱；门禁照常生效 |
| A4 | 执行 | 跑测试、合并、部署 | 跑测试限本地/沙箱；合并/部署永远需门禁 5 与人类授权 |

1. 本规范配套的全部托管平台 workflow 自主权上限为 **A2**；A3/A4 由 Agent 在本地开发环境执行，合入门禁（§2.16.3 DoD、门禁 5）不因自动化而豁免。
2. **客户端兼容第二维度**：支持 pre-write Hook 的客户端（Claude Code、Gemini CLI 等）三层全开（Hook 建议 + 脚本强制 + CI 边界）；不支持 Hook 的客户端/IDE 退化为 Git Hook（staged/stop）+ CI 兜底，**语义不变、防线后移**，不得因客户端差异放弃任一门禁。

#### 2.17.4 治理配置自测试（Golden Cases）

1. 门禁脚本（`agent-gate.sh`）与 hooks/CI 模板属于"治理配置"，自身必须可回归：`tests/run-tests.sh` 在临时 Git 仓库中构造合规/违规状态（begin 缺产物、L2 角色不独立、pre-write fail-closed、staged/stop/ci 各门禁、度量输出），断言退出码与输出。
2. 修改 `agent-gate.sh`、hooks 或 CI 模板的变更必须先跑通全部用例再合入；用例与实现同仓同版本。
3. 测试套件零依赖（bash 3.2+ 与 git），macOS/Linux、任意 IDE 终端均可运行，作为 §2.13.4 自动化门禁对治理配置自身的适用。

#### 2.17.5 管线度量（metrics）

1. `agent-gate metrics` 以 JSON Lines 输出每个变更的阶段时间戳与间隔：`intent_ts` / `spec_ts` / `plan_ts` / `first_code_commit_ts` / `test_evidence_ts` / `changelog_ts`，间隔 `intent_to_spec_s` / `spec_to_plan_s` / `plan_to_code_s` / `code_to_evidence_s` / `intent_to_changelog_s`，以及 `delivery_ready`（05+07+09 三件齐备才为 true）。
2. 度量为 A0 只读观察，纯 git 历史推导、零第三方依赖；任一端点缺失输出 `null`，禁止推测补值。
3. 用途：识别管线瓶颈（如 `spec_to_plan_s` 过长 = 方案阶段积压）与交付就绪状态；**禁止用度量数值替代 DoD 判定（§2.16.3）**。

## 3. 变更执行全流程检查清单（Checklist）

## 4. Changelog 格式规范（核心交付物）

`09-changelog.md` 记录每次具体变更，是跨会话、跨 Agent 的承上启下记忆载体。每个 CHG 必须包含本节的追踪映射、现象、分析、根因、方案、测试结论、角色签署、执行检查清单与未动项；命中 §2.6 时「方案」含配置/DB 清单，进入发布时另加「发布与回滚记录」字段。**每个 CHG 的「追踪矩阵映射」节为短引用**（需求/设计/测试编号 + 链接 `01.5-rtvm-matrix.md`），完整矩阵在独立文件 `docs/<feature>/01.5-rtvm-matrix.md`（§1.2）——两处必须同步回填：

```markdown

#### 追踪矩阵映射 (Traceability)

- 对应设计：`DES-xxx`（见 03-modification-plan.md）
- 对应测试：`TC-xxx`（见 04-test-scripts.md / *Test.java）

#### 现象
[必填] 描述用户或系统观察到的具体异常。
```

## 5. 常见违规行为与拦截策略（Anti-Patterns）

| 违规行为 | 严重等级 | 门禁拦截策略 |
|---|---|---|
| **跳过文档直接改代码** | 🔴 严重违规 | 触发【门禁 1】拦截，必须先回退代码，更新 `01-spec.md` 和 `03-modification-plan.md` 后重新开始。 |
| **改完代码不写/不跑测试** | 🔴 严重违规 | 触发【门禁 2 & 3】拦截，禁止宣称完工，必须补全 `TC-xxx` 并执行 `mvn test` 提供真实终端输出。 |
| **口头宣称“测试已通过”** | 🔴 严重违规 | 触发【门禁 3】拦截，无脱敏测试摘要、退出码和受控原始日志制品链接者一律判为未完成。 |
| **同一 Agent/开发者自测、自审、自批** | 🔴 严重违规 | 违反门禁 5：重新分派独立测试与 Review；高风险变更补人类 Release Owner 授权后方可合入。 |
| **将含敏感用户数据（PII）、密钥或 token 的原始日志写入 Git 文档** | 🔴 严重违规 | 违反门禁 3/§2.9：立即删除并按泄露流程处置；文档仅留脱敏摘要与受控制品链接。 |
| **门禁例外无授权、无到期时间或被 Agent 自批** | 🔴 严重违规 | 违反 §2.13.4：例外无效，变更退回；由有授权人重新评估风险与补偿措施。 |
| **孤儿代码（无 REQ/TC 映射）** | 🟡 中度违规 | 触发【门禁 4】拦截，要求在 RTVM 矩阵中补充上游需求来源与下游测试用例。 |
| **只更新 changelog 追踪矩阵、不回填独立 RTVM 矩阵文件** | 🟡 中度违规 | 触发【门禁 4】拦截，要求回填 `docs/<feature>/01.5-rtvm-matrix.md`（§1.2），含验证状态、编号顺序核对与四维链路。 |
| **RTVM 四维链路断环（REQ→DES→TASK→TC 任一环缺失）** | 🔴 严重违规 | 需求必须有设计、设计必须落任务、任务必须产出测试；断环即回填补齐，禁止跳环。 |
| **改动调用点打点未断言（执行≠覆盖）** | 🟡 中度违规 | 违反门禁 2 断言完整性，要求补充断言（如可观测记录事件/里程碑/终止原因）。 |
| **只跑受影响用例、跳过全量回归** | 🟡 中度违规 | 违反门禁 2 全量回归强制，要求跑 `mvn -pl <module> -am test` 全套件再合入。 |
| **测试报告覆盖/改写历史批次结果** | 🔴 严重违规 | 违反门禁 3 批次保留：`05-test-results.md` 历史批次原文/状态不得覆盖，须追加独立小节（§N）；修订须加「修订说明」。 |
| **标准升级未回填存量文档** | 🟡 中度违规 | 违反 §2.14：标准新条款必须回填所有既有功能文档，未回填视为未落地。 |
| **CHG 未回写方案正文 / 未拆任务（无豁免标注）** | 🟡 中度违规 | 违反阶段 3/9：CHG 必须回写 `03-modification-plan.md` 正文并拆 T 任务（或显式豁免标注），禁止只登记。 |
| **变更执行检查清单无落点（只在会话/工作区勾选）** | 🟡 中度违规 | 违反 §3 落点规则：勾选清单必须随 CHG 归档 `09-changelog.md`「变更执行检查清单」字段。 |
| **覆盖丢历史（活文档/配置/批次无追溯 / 改写已闭合 CHG / 06.5 改旧 CFG 行）** | 🔴 严重违规 | 违反 §2.15：历史批次/旧 CFG 行/已闭合 CHG 禁止覆盖，须追加或加「修订说明」。 |
| **RTVM 编号跳号/重号/重排历史编号** | 🟡 中度违规 | 违反 §1.2 编号顺序规则，要求按连续递增修正，历史编号禁止重排。 |
| **阶段产物缺失或未达规格下限** | 🟡 中度违规 | 按 §2.5 必含清单逐项核对，缺失即打回补齐后再进入下一阶段。 |
| **未做背景调研/影响分析直接出方案改代码（片面改动）** | 🔴 严重违规 | 违反 §2.16.1 第 4 步与 §2.5 阶段 2「先分析后方案」：退回补齐业务/技术/风险三维影响分析与背景调研结论；技术选型无 ≥2 候选对比同理打回（阶段 3）。 |
| **未经 Thought 直接改代码/文档（"上来就改"）** | 🔴 严重违规 | 违反 §2.16.2 ReAct 铁律：退回补全局影响分析（业务/技术/风险三维）与 Thought 记录；已产生的改动须重新评估影响面后方可保留；09「执行记录（ReAct）」缺 Observation 记录的阶段视为未闭环。 |
| **测试覆盖维度静默裁剪** | 🟡 中度违规 | 违反 §2.5 阶段 4：未设计的覆盖维度必须逐维度显式标注「不适用，理由」，退回补标注或补用例。 |
| **只口头宣称"已验收 / 已按规范产出"而不逐条抄录该阶段验收标准** | 🔴 严重违规 | 违反 §2.5 总则：该阶段判定未完成，退回逐条抄录并勾选；A 层必须附校验命令与实际输出，B 层必须附独立角色签署（含 Agent 标识）。 |
| **A 层校验只口头宣称"通过"、不附命令与输出记录** | 🔴 严重违规 | 违反 §2.5 A 层：必须把校验命令与实际输出记入 09「变更执行检查清单」，无记录视为未验收（开发 Agent 不得自评 B 层）。 |
| **代码注释只写 WHAT 不写 WHY** | 🟡 中度违规 | 审查不予通过，要求在修改处补充 `// CHG-xxx` 说明业务原因与上下文。 |
| **新增字段/接口无契约注释** | 🟡 中度违规 | 要求按 §2.5 阶段 5 补充字段可空性、含义与变更背景注释。 |
| **改配置/DB 不记录（无 06.5 文档、无映射）** | 🔴 严重违规 | 命中 §2.6.1 却未维护 `06.5-deployment-config.md` 与 CFG/DB 映射矩阵 → 判未闭环，禁止上线。 |
| **直接手改生产库 / 无恢复方案** | 🔴 严重违规 | 数据库变更必须走版本化脚本，并提供回滚或经批准的前向修复、备份与校验方案；手改生产库一律拦截并处置。 |
