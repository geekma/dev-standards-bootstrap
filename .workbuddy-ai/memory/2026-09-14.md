# 2026-09-14

## 排查：check-standards-compliance.sh 基线硬编码 origin/main

- 现象/疑问：用户提出脚本默认基线 `origin/main` 在「主线为 master」的仓库不存在。
- 事实核对：本仓库 dev-standards-bootstrap 实际默认分支是 `main`（`origin/HEAD -> origin/main`，`git show-ref` 无 master ref），所以 main 场景应属安装了模板的目标仓库，不是本仓。
- 根因：把三件事混为一谈 —— (a) 需要基线（git 语义刚需，`BASE...HEAD` 三点号 = merge-base 语义）；(b) 需要默认值（模板必需）；(c) 默认值写死 `origin/main`（缺陷）。`agent-gate.sh` 走 `--base` 由调用方提供，pre-push 用 `@{upstream}`，只有 compliance.sh 与 workflow 的 `|| 'main'` 回退里出现字面量。
- 实测失效模式：
  1. master 主线仓库 → `fatal: ambiguous argument 'origin/main...HEAD'`，退出码 128（fail-closed 但不可自愈、报错难懂）。
  2. 浅克隆 CI（actions/checkout 默认 fetch-depth:1）→ origin/main 不存在；governance workflow 特意写了 `fetch-depth: 0`。
  3. 危险修法：顺手加 `|| true` → CHANGED_FILES 为空 → 打印 ✅ → **静默放行（fail-open）**。
- 实证两点号危害：`git diff master..HEAD` 会把 master 上他人提交的 `src/other.js` 计入本分支变更 → 假阳性；三点号只出 `docs/f1/01-spec.md`。
- 已验证补丁：五级基线解析链（显式参数 → CI_BASE_REF → `refs/remotes/origin/HEAD` → origin/main|master|trunk|develop → 本地同名分支 → 全失败 exit 2）。在 master 主线仓库实测解析到 `master` 并正确命中源码变更检查。
- 关键结论：**不要猜本地当前分支**（`git branch --show-current` 是错方向——要的是「合入目标」不是「我在哪」）；CI 里最权威的是 PR 的 base_ref/base.sha，只有本地才需要启发式兜底。
- 未落地：改动会命中 is_code_path（resources/templates/*.sh）→ 按本项目规范属源码变更，需 `docs/changes/<CHG>/` 产物；且 T12（run-tests.sh）与 A2（audit-standards-src.sh）双守护要求 gate 与 compliance 的扩展名清单同步，抽公共函数时须一并考虑同步义务。等用户确认后再起 CHG。
- 附带发现：`github-agent-governance.yml` 的 `github.base_ref || 'main'` 在 push 事件下 base_ref 为空 → 退化为 origin/main = 被推分支自身 → diff 为空 → 门禁空转。
